预期：HEAD 原始大小减少几十 MB 到一百多 MB。这一步主要改善工作区，对 clone 体积帮助有限。

### C. 历史处理（见 §6 决定 1）

两种做法选一种：

**C1. 用 `git filter-repo` 重写现有仓库历史**

- 删掉 4 个 `.7z`，以及 §2.C 里确认只存在于历史中的大文件（按路径列清单，不用"大于 N MB 全删"这种一刀切）。
- 预期可达 blob 从约 461 MB 降到 150–200 MB。
- 所有 commit SHA 都会改变：所有分支、tag、已有 clone 全部作废，需要强推。
- 历史 commit 保留提交信息，但里面被删的文件取不回来。

**C2. 新开公开仓库，只放一个干净的初始提交**

- 用当前 HEAD 的入库文件做一个 orphan 初始提交，推到新的公开仓库。
- 现有私有仓库原样保留，作为完整历史存档，不做任何破坏性操作。
- 预期公开仓库 clone 约等于 HEAD 压缩体积（约 150 MB，B 做完后更小）。
- 公开仓库没有早期历史；需要追溯的时候去私有仓库查。

### D. 执行安全（无论选 C1 还是 C2）

- 在**全新的独立 clone** 里操作（`git clone`，不用 `git worktree`），只包含入库文件。
  不 junction、不 symlink、不复制 `gt6_code/`、`gt6_referencable_port_code/`、`gt6u_code/`、
  `gtceu_code/`、`gt6_dump/`、`ktfruaddon/`、`gt6_tfru/`。
- 主工作副本不运行 filter-repo，也不 reset、不 clean。
- 操作前把现有仓库做一份 `git clone --mirror` 备份，放在工作区之外。
- 强推（C1）或新仓库推送（C2）之前，由用户当场确认。
- 完成后在新 clone 里跑一次 `./gradlew assemble` 和 `python tools/verify.py dev`，确认能编译。

## 6. 决定（2026-09-29 用户确认）

1. **历史处理选 C1：用 `git filter-repo` 重写现有仓库历史，然后强推。** C2 不做。
   - 删除清单按路径逐条列出，写进 `tools/repo_slimming/history_strip_paths.txt`，
     由用户在执行前审阅；不用"大于 N MB 全删"一刀切。
   - 顺序固定：A、B 先以普通提交合入并且 CI 变绿，再做 C1。这样重写的对象是已经清理过的 HEAD。
   - 强推前除 mirror 备份外，还要确认没有其他未合并的分支（`prep/*` 等）；
     有的话先合并，或者由用户决定放弃。强推后这些分支都会作废。
     2026-09-29 检查：远端只有 `origin/main`（1 个提交，只含 `LICENSE`）没合进 `master`，
     另有 tag `archive-2026-08-21`。用户决定：强推时**删除**远端 `main` 分支和这个 tag
     （本地和远端都删），不重写、不保留。否则 tag 会让旧历史对象继续可达，GitHub 上的体积降不下来。
   - 强推后，本机主工作副本**原地对齐**（2026-09-29 用户选定），不重新 clone，不搬参考树：
     1. 对齐前工作区所有改动先提交；
     2. `git fetch origin`，然后 `git switch -C master origin/master`；
     3. `git diff <旧 master 提交> <新 master 提交> --stat` 必须为空（新旧最新提交的文件逐字节相同）；
        不为空就停下，交给用户；
     4. 删除本地 tag `archive-2026-08-21`；
     5. 此后不使用 `git push --all` / `git push --tags`，避免把旧历史推回去。
     本机 `.git` 里的旧对象暂时保留；是否以及何时 `git gc --prune` 由用户决定，本卡不执行。
   - 前提：filter-repo 只删**只存在于历史中**的路径。strip 清单里任何一条若仍在 HEAD 里，
     就先在 B 阶段用普通提交删掉，保证重写后最新提交的文件与重写前完全一致。
2. **本卡占 unique-active。** 执行 C1 那一刻不能有别的卡在改代码。本卡关闭前不开新的内容卡落地。
