## `dump_policy`（SOURCE_BACKED）

R0 `network_contract.json` 的问题是：Dump 与 transfer / storage 差在哪，
以及 Dump 盖板在网上冲掉或丢弃什么。本卡回答这个问题，**不改** sealed
R0 JSON。

来源：

- `src/main/java/gregapi/cover/covers/CoverLogisticsGenericDump.java`
- `src/main/java/gregapi/cover/covers/AbstractCoverAttachmentLogistics.java`
- `src/main/java/gregtech/tileentity/multiblocks/MultiTileEntityLogisticsCore.java`

仓库指针：`https://github.com/GregTech6/gregtech6` @ `3703e40308c8c030763fd6297dea8b210d2a77b1`
（`tools/machine_tree_cover_multiblock_policy.json` 已钉 raw URL）。

### 盖板本身

`CoverLogisticsGenericDump` 几乎是空类：贴图
`machines/covers/logistics/generic/dump`，以及
`usePriorities() { return F; }`。它不搬物品、不搬流体、不声明库存。
螺丝刀优先级对 Dump **关闭**。放置规则走物流盖板基类：只能贴在
`ITileEntityLogistics` 且 `canLogistics` 的宿主上，并断开该面连接。

所以 Dump **不是** 第四种 Generic transfer，也 **不是** 第二种 Generic
storage。

### 真正执行器

扫描、排队和搬运都在 `MultiTileEntityLogisticsCore` 的服务器 tick 里。
Core 把 Dump 盖板邻接库存收进 `tStackDumps`（只有物品列表，没有对应的
流体 dump 列表）。同一 tick 的顺序是：

1. 导入 / 导出（按过滤档 Generic → Semi → Filtered）
2. 整理：Generic storage → Filtered / Semi storage
3. **Dump**：从 Generic **物品** storage 搬到 Dump 邻接库存

来源调用：

```text
ST.move(tImport.mTarget, tExport.mTarget, tFilteredFor, F, F, T, F, 64, 1, 64, 1)
```

`tFilteredFor` 是网上已登记的过滤物品集合。Dump **不把物品销毁**，只搬进
Dump 盖板对着的容器。精确 invert / 过滤参数在实现 Logistics Core 时对照
`ST.move`，本卡不在管网上发明一套。

### 直接推论

| 问题 | 答案 |
| --- | --- |
| 与 transfer 的差 | Dump 不是按方向寻址端点的导入/导出。它是 Core 在其它事务都做完之后的最后一档溢出 |
| 与 storage 的差 | Dump 不声明可查询库存；它是溢出出口 |
| 冲掉或丢弃什么 | 把 Generic 物品仓储里、过滤集合管不到的剩余物品搬进 Dump 邻接容器。不是虚空删除 |
| 流体 | 钉住的 Core 只收集 `tStackDumps`。本卡不发明流体 Dump |
| 现有管网能不能做 | **不能** 作为 SOURCE_BACKED 的第七件盖板。物品/流体/Generic 管网没有这套优先级扫描，也没有 Core 的 CPU / 能量 tick |

因此：把 Dump 做成 Generic sidecar 第四行，等于用 DESIGN_POLICY 发明
void-vs-flush。本卡禁止。
