1. `tools/` 根目录那 5 个没有任何引用的大 JSON（`chemical_axis_source_denominator.json`、

预期：HEAD 原始大小减少几十 MB 到一百多 MB。这一步主要改善工作区，对 clone 体积帮助有限。

### C. 历史处理（见 §6 决定 1）

两种做法选一种：

**C1. 用 `git filter-repo` 重写现有仓库历史**

- 删掉 4 个 `.7z`，以及 §2.C 里确认只存在于历史中的大文件（按路径列清单，不用"大于 N MB 全删"这种一刀切）。
- 预期可达 blob 从约 461 MB 降到 150–200 MB。
- 所有 commit SHA 都会改变：所有分支、tag、已有 clone 全部作废，需要强推。
- 历史 commit 保留提交信息，但里面被删的文件取不回来。

**C2. 新开公开仓库，只放一个干净的初始提交**

- 用当前 HEAD 的入库文件做一个 orphan 初始提交，推到新的公开仓库。
- 现有私有仓库原样保留，作为完整历史存档，不做任何破坏性操作。
- 预期公开仓库 clone 约等于 HEAD 压缩体积（约 150 MB，B 做完后更小）。
- 公开仓库没有早期历史；需要追溯的时候去私有仓库查。

### D. 执行安全（无论选 C1 还是 C2）

- 在**全新的独立 clone** 里操作（`git clone`，不用 `git worktree`），只包含入库文件。
  不 junction、不 symlink、不复制 `gt6_code/`、`gt6_referencable_port_code/`、`gt6u_code/`、
  `gtceu_code/`、`gt6_dump/`、`ktfruaddon/`、`gt6_tfru/`。
- 主工作副本不运行 filter-repo，也不 reset、不 clean。
- 操作前把现有仓库做一份 `git clone --mirror` 备份，放在工作区之外。
- 强推（C1）或新仓库推送（C2）之前，由用户当场确认。
- 完成后在新 clone 里跑一次 `./gradlew assemble` 和 `python tools/verify.py dev`，确认能编译。
