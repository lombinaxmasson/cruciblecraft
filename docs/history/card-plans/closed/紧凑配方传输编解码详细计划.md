## 0. 决策

崩溃不是「一个物品挂一大坨 component」。`MaterialItem` 和 bath identity
都是空 `Item.Properties()`；栈上通常只有 id / count。真正炸的是：

```text
GT6: 1 个 toolHead × 上千 meta
  -> CC: 独立 registry id（政策：不折进 prefix，不用共享物品+材料 component）
  -> compact 合同：exact relations only；parameterized 现为 fail-closed
  -> 1 semantic family = 1 JSON RecipeHolder = 1 NBT
  -> CompactGTRecipeFamilySerializer
       ByteBufCodecs.fromCodecWithRegistries(CODEC)
  -> FriendlyByteBuf.readNbt() / NbtAccounter 2,097,152
```

`gt.recipe.bath#0025` 不是孤例。签发时 live tree 里：

| 事实 | 数 |
| --- | --- |
| compact RecipeHolder | 5651 |
| compact relations 合计 | 77319 |
| JSON > 1 MiB 的 family | 39 |
| 其中 tool_head | 19 |
| 其中 bath remainder exact_multi | 11 |
| 其中 bath identity exact_multi | 9 |
| `#0025` 磁盘 JSON | 1,168,597 bytes / 1116 relations |
| `#0025` gzip -6 | 75,690 bytes |
| `#0025` 公共配方形状 | 1（只换物品 / 流体 id） |
| `#0025` 输入 / 输出 / 流体配置 | 147 / 9 / 15 |

现有 `sync_bytes` 门没抓住，因为量的不是这条限制：

1. 64 MiB 是 **portfolio 总和**，不是 per-entry；
2. `CompactRecipeFamilyProvider.payloadBytes()` 只计 id / 基础数字 / 列表长度，
   漏掉 Ingredient、ItemStack、FluidStack、provenance；
3. publication shard（ceiling 128）是 **lookup 路由**，不是传输分包；
4. on-demand 只影响同步完成后的物化，不减小 RecipeHolder 体积。

本卡答三道题：

| 题 | 答 |
| --- | --- |
| 要不要改物品注册 | 不要。独立 registry id 政策不动 |
| exact relation 能不能改成「任意工具头 + 油」 | 不能。最终关系集合仍必须精确 |
| 传输格式能不能压缩重复 | 能。合同约束的是解码后的关系集合，不是线上逐条复述完整对象 |

```text
runtime/compact-recipe-wire-codec
```

## 1. 完成后应该成立的工作流

```text
measure live compact RecipeHolders with the current StreamCodec
  -> fail closed if any entry still uses NBT-backed fromCodecWithRegistries
replace CompactGTRecipeFamilySerializer.streamCodec()
  keep MapCodec / datapack JSON
  write a bounded binary StreamCodec
  dictionary-encode repeated items / fluids / provenance
  decode limits before allocating
encode every live compact entry
  max_recipe_entry_wire_bytes  <= 524288   # 512 KiB product ceiling
  no entry uses readNbt()
round-trip decode == encode input
  relation fields, stable_id, fingerprint
dedicated client update_recipes no longer trips NbtAccounter
integrated client still reuses server epoch
EMI / RecipeMap enumeration still sees the same logical relations
  -> COMPACT_RECIPE_WIRE_CODEC_READY
       or BLOCKED
```

关键分界：

1. 语义 family 仍是 1 个 `family_id`。T48 `145 / 34091 / 3532` 分母不重开。
2. datapack JSON 本卡默认不动。A 成功就不要碰 `src/recipe_generated/**`。
3. 若 A 之后仍有条目超过 512 KiB，才允许走 §3.2 的 transport fragment。
   fragment 必须带 semantic family id + index/count + digest，禁止给
   `family_id` 加后缀冒充新 family。
4. parameterized / 自定义 RecipeManager 旁路是后卡，本卡不要。
5. 关闭后 `next_unassigned = true`。账本内容下一张仍是 Item Network
   Core，未签发。不预分配物流网 / 核电 child。

## 3. 权威分母

本卡不拥有 family。分母是 **传输单元** 和 **硬上限**。

### 3.1 必须修的传输单元

所有 `type = cruciblecraft:compact_gt_recipe_family` 的 RecipeHolder。
代表崩溃条目是

```text
src/recipe_generated/resources/data/cruciblecraft/recipe/bath/identity/gt_recipe_bath_0025.json
family_id          = gt.recipe.bath#0025
publication_group  = cruciblecraft:bath/identity/tool_head
relations          = 1116
```

验收不得只测这一条。39 个 > 1 MiB JSON 都要过 encode 门；5651 条都要
报大小。

原版硬上限（不得改游戏代码去抬）：

| 限制 | 值 | 本卡关系 |
| --- | --- | --- |
| `NbtAccounter` / `readNbt` | 2,097,152 | A 之后这条路径必须消失 |
| `ClientboundCustomPayloadPacket` | 1 MiB | 整包仍可走 NeoForge splitter |
| 默认集合解码 | 65,536 | 自写 codec 必须更严 |
| 现有 `RECIPE_SYNC_BUDGET_BYTES` | 64 MiB 总和 | 保留为聚合门；**不够**当 per-entry |

本卡产品门（`DESIGN_POLICY`）：

```text
max_recipe_entry_wire_bytes  = 524288     # 512 KiB；实测 encode 后
decode_relations_ceiling     = 4096
item / fluid IO per relation = 16
string fields                = 显式最大长度
```

512 KiB 是产品门，不是原版上限。贴着 2 MiB 过线算本卡失败。

### 3.2 仅当 A 不够：transport fragment

触发条件：A 落地后，仍有 live compact entry 的真实 encode > 524288。

合法做法：

- 保留 semantic `family_id` / `stable_id` / publication group；
- 增加 fragment envelope：`semantic_family_id`、`fragment_index`、
  `fragment_count`、family digest、relation 总数；
- `CompactRecipeFamilyProvider` 在 dedup / fingerprint **之前**重组；
- authored family 计数仍按 semantic family，不得把 fragment 算进
  T48 `145`。

非法做法：给 `gt.recipe.bath#0025` 改成 `#0025_part0` 充数。

触发 §3.2 才允许改 generated JSON 并 **重 seal** T48。没触发就不要动
seal。

### 3.3 本卡 `deferred`

- `ParameterizedSpec` / `bath_identity_matrix_v1`（模板 + 允许元组）
- 自定义 compact manifest，绕开 vanilla `update_recipes`（方案 C）
- 把 tool_head 折进 material prefix 或共享物品 + 材料 component
- 重测 / 改写 T48 on_demand 胜出理由

### 3.4 本卡 `out_of_scope`

- 提高或取消 `NbtAccounter`
- 只把 materialization 改成 on-demand / hybrid
- Item Network Core、封面网、核电、原版替换余量
- EMI 插件重写（A/B 不改 `RecipeMap.entries()` 语义）
- 玩家发行 / RC soak

兄弟 serializer（`GTRecipeEntrySerializer`、`MaterialRule.STREAM_CODEC`）
也走 `fromCodecWithRegistries`。本卡扫描它们的真实 encode；只有超
512 KiB 的才改。不要借机重写全部配方 codec。

## 4. 实现约束

- datapack `MapCodec` 保持可读；网络 `StreamCodec` 不许再包一层 NBT。
- 字段级二进制。建议复用 `ResourceLocation.STREAM_CODEC`、
  `Ingredient.CONTENTS_STREAM_CODEC`、`ItemStack.OPTIONAL_STREAM_CODEC`、
  `FluidStack.OPTIONAL_STREAM_CODEC`。
- family 公共字段（duration / EU / action / source recipe / source kind）
  能提升的就提升；relation 只写字典索引、stable-id、evidence hash。
- 64 位 stable-id 后缀和 32 字节 evidence hash 写二进制，不写 hex 字符串。
- 解码先读 count，超限立即拒绝，再分配集合。
- 集成客户端继续复用 server epoch，禁止 `INTEGRATED_CLIENT` 重建。
- 独立客户端仍从同步后的 RecipeManager 重建 compact snapshot。
- 不得把「任意 raw pickaxe head + 油」写成 parameterized 蒙混过关。
- 不得改 `BathIdentityCatalog` 注册循环来「缩小配方」。

## 7. 撤回

实施中发现阻塞时只有三种合法结果：

1. A 不够则走 §3.2，写清为何某 family 二进制仍超 512 KiB；
2. 保持 `BLOCKED`，写清缺的是 codec 边界、dedicated-client 证据还是
   seal 重算；
3. 正式撤回并重签，保留旧卡路径。

不得用提高 NBT 上限、关掉 EMI、或只测集成客户端来冒充 READY。
不得把本卡写成 T48 重做或 Item Network Core 已开工。

关闭时：本计划移到 `card-plans/closed/`，补 stage archive 与 work log；
更新 history index、roadmap、workflow、verification、known-issues 与
账本第 0 节；不重写 sealed R0 / T48 artifact（除非 §3.2）；不自动创建
Git commit。
