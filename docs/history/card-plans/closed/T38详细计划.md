## 0. 先读这一节

### 0.1 固定 work set 与两个分母

Host 与 target map 均为 `cruciblecraft:roaster`。Family 恰好 29 个，来自 T37 topology：

```text
gt.recipe.roaster#0000
gt.recipe.roaster#0001
gt.recipe.roaster#0003 ... gt.recipe.roaster#0029
```

GT6/T35 Roaster family 编号中不存在 `#0002`；这不是一个被 T38 延期或遗漏的 family，
不得补 placeholder，也不得把它加入 gap。

T38 不是“29 families = 29 source rows”。T35 family ledger 冻结的 ordinary 分母为：

| family | ordinary source rows |
| --- | ---: |
| `#0000` | 38 |
| `#0001` | 3 |
| `#0003` | 2 |
| `#0010` | 3 |
| `#0014` | 3 |
| 其余 24 个 singleton family | 24 |
| **合计** | **73** |

因此本卡同时冻结：

```text
family_count = 29
source_rows = 73
expected_authored_family_entries = 29
expected_logical_relations = 73
```

29 低于常规 50–200 family 波次带宽，但 73 source rows 已形成有界实测 workload；这是
Roaster host-complete small-wave 的固定例外，禁止用无关 family 凑数。

### 0.2 ordinary row 不是 template total

T35 `expanded_count` 是本卡应关闭的 ordinary rows。部分 Roaster template 的
`template_total_rows` 更大，因为同一 template 中还有不属于本卡的分类行。Source replay
必须用 T22.5 row classification 交叉筛选，不能把整张 template 的所有 raw rows 搬进 T38，
也不能重复发布已经由其他卡拥有的 row。

T35 历史快照中这些 family 因当时缺少 Roaster host 而是
`out_of_scope / portfolio:track_a/missing_host`。Current opening 必须按 overlay 链解释：

```text
T35 historical family identity
  -> T36 roaster host_exact + in_scope_1x reissue
  -> T37 topology owner = T38
  -> T38 planned / incomplete / source_backed / pending
```

Builder 不得要求 T35 原始 disposition 已经是 `planned`，也不得回写 T35 来伪造 current
状态。

### 0.3 Load opening

这些值必须保留 T37 artifact 的原始测量语义。T38 closing 按 T14 policy 对 sum、
sum-interval 与 max-interval 轴分别聚合，不得把所有 runtime 轴机械相加。

Hard ceiling 不得在本卡提高。T37 的 14 eager / 36 lazy / cache 8 只属于 Assembler
50-row workload；T38 必须在实际 73-row Roaster workload 上独立实测。

### 0.4 Gap opening 与 closing

T37 closing 的 current ordinary recipe gap 是 5,668 families。若 T38 29 family 全部真实
关闭，理论 planning baseline 为：

```text
5,668 - 29 = 5,639 families
```

5,639 不是开卡时即可宣布的 current 数字。只有 T38 closing census delta 证明 29 个
identity 全部从 planned/incomplete/pending 转为 implemented/closed/measured 后，才允许
把正式重算结果交给下一波。

### 0.5 一句话判据

> 从 pinned GT6 Roaster dump 无损冻结 topology 指定的 29 family / 73 ordinary rows，

> materialization strategy，并以 current 玩家路径、load ledger、census delta 和 gap
> recompute 共同关闭 T38。

## 1. 固定产品与架构前置

### 1.1 三个独立验收轴

1. **Closure**
   - 29 family / 73 source rows 全部有唯一 compact source、generated entry 与 runtime id；
   - source / generated / runtime / EMI 集合相等；
   - Roaster host、机器供能、输入获得与输出去向闭合。
2. **Fidelity**
   - 73 rows 的输入输出、数量、动作、概率、duration、energy、special value、buffering 与
     shadow order 来自固定 source；
   - `SOURCE_BACKED`、`SOURCE_DERIVED`、`DESIGN_POLICY` 分开记录；
   - unmapped 或 runtime 无法表达的字段 fail closed，禁止静默丢弃。
3. **Load**
   - 每个 family 分别记录 source/authored/logical/eager/lazy；
   - card-level cache、sync、reload、index、memory、allocation 与 lookup 只记录一次；
   - actual 73-row 候选测量决定生产策略，正常选择不越 cumulative soft budget。

### 1.2 T37 runtime 必须先解除的两个 stage 特例

T37 已建立 host-neutral codec/provider，但当前生产接线仍有两个不能直接带入 T38 的限制：

1. `GTRecipeMapLoader` 向 `prepareByTarget` 传入单个
   `CompactRecipeFamilyProvider.t37ProductionPolicy(compactSources)`。加入 Roaster 后若保持
   此接线，T38 会继承 T37 selector，违反独立实测。
2. `CompactGTRecipeFamilyGeneratedSupport` 只读取每个 authored entry 的
   `relations[0]`。T38 含多-row family，first-relation-only 测试会漏掉 44 条 relation。

T38 必须把 production policy 解析改为 target/stage-aware，并让 generated test support
遍历全部 relations。修改后必须证明：

- Assembler 仍恰好 14 eager / 36 lazy / cache 8；
- Roaster 使用 T38 decision 派生的独立 policy；
- 两个 target 可在同一 epoch 同时 prepare、enumerate、lookup 与 reload；
- T37 stable ids、fingerprint、load partition 和闭卡证据不被追溯改写。

这两项是 T38 正确性的前置，不是顺手重构。

### 3.1 独立生成根


并把 `src/t38_recipe_generated/resources` 加入 `sourceSets.main.resources`。生成器只消费
committed T38 compact source，不在普通 write 中扫描 raw dump。

每个 family 生成一个 authored compact entry；多-row family 的所有 relation 必须保留在
同一 entry 的 `relations[]`：

```text
source families = 29
source relations = 73
authored entries = 29
logical relations = 73
```

文件名保持 T37 已验收的确定性规则：

```text
gt.recipe.roaster#0000 -> gt_recipe_roaster_0000.json
...
gt.recipe.roaster#0029 -> gt_recipe_roaster_0029.json
```

生成器删除 T38-owned stale 文件，不触碰 T37 或其他 generated root。连续运行两次，第二次
必须零变化。

### 3.2 Stable id

Runtime stable id 按 source revision 下稳定的 family identity 与 row fingerprint 派生。
不得使用 registry index、生成顺序或 family 内当前数组位置作为唯一身份。

T38 runtime namespace 固定为 `cruciblecraft:t38/{16-hex-row-fingerprint}`；一个多-row
family 必须产生多个不同 stable ids。

Source recipe 顺序变化但内容不变时：

- stable id 保持；
- source index drift 单独报告；
- 新增/删除/字段变化产生明确 delta；
- 同一 family 的 38 rows 不能折叠成一个 runtime id。

### 3.3 Per-target production policy

`CompactRecipeFamilyProvider.prepareByTarget` 应接收按 target map 解析的 policy，而不是一个
全局 T37 policy。可采用 policy map 或 resolver，但必须满足：

```text
cruciblecraft:assembler -> frozen T37 decision
cruciblecraft:roaster   -> derived T38 decision
unknown target policy   -> fail closed
```

Policy 选择不能由 authored id 字典序意外跨 host 互相影响。T38 hybrid 候选若使用 eager
selector，必须按 73 个 relation stable ids 选择，而不是每个 family 只检查
`relations[0]`。

### 3.4 Runtime coexistence

Java tests 至少覆盖：

- 29 authored Roaster definitions 聚合为一个 Roaster compact snapshot；
- snapshot 有 73 logical ids；
- Assembler 与 Roaster 在同一 prepared epoch 共存；
- unknown map / missing policy / duplicate authored id / duplicate stable id fail closed；
- integrated client 复用 server snapshot，dedicated client 重建等价 snapshot；
- reload 失败保留旧 epoch；
- enumeration 不预热或撑破 lazy cache；
- T14 Extruder family 与 T37 Assembler 行为保持不变。
