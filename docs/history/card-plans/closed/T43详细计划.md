## 1. 决策与签发边界

`tools/t42_wave_candidates.json` 的 Drying 1-family `priority_intent` 只是排序提示，不满足
当前普通 recipe wave 的批量目标，故不作为 T43 production lock。本卡改为处理 Smelter
中可由一个严格、有限的 source-object catalog 解除的 stone cohort：

```text
cohort A
  host = cruciblecraft:smelter
  owner = identity_mapping/unmapped
  every missing runtime id matches item_inputs:gregtech:gt.stone.*
  no other missing runtime id, form, fluid, B0, unique-object,
    vanilla-proof, lossy-alias, or unsupported-semantics blocker
  = 406 complete families / 406 relations

cohort B
  host = cruciblecraft:smelter
  current_owner = recipe_wave/smelter
  = 1 complete ready family / 1 relation

T43 production-lock target = A + B = 407 families / 407 relations
```

R0 必须从 repaired T42 overlay、T42 owner lock 和 current census 再执行上述规则，重新写入
`selection_sha256`。407 是待复算的 lock 目标，不是允许在旧 overlay 上静态预扣的
closing 结果。若任何 cohort A family 出现第二 blocker，必须整个 family 留在 current gap；
不得用另一 family 静默填补数量。

下列 Smelter 内容明确不属于 T43：

- 14 个有 hazmat armor 或 `gt.meta.storage.{ingot,plate}` 输入的非 stone unmapped
  families；
- `gt.recipe.smelter#0111` 的无 runtime-id 残差；它缺少可审计 source identity，不能借
  stone catalog 关闭；
- 286 个 block-object、106 个 multiitem、36 个 tool-head family，以及其他 GT prefix
  object-expression owner；
- 26 个 material-form、8 个 B0、114 个 multi-axis、2 个 recovery-evidence-needed
  family；
- 已在 `later:recycling` 的 1,817 个 proven Smelter recovery family；它们属于 deferred
  ordinary ledger，不是 T43 completion。

因此，本卡不是 “Smelter 全量导入”，也不是 source row 数量的扩张；它只关闭 source identity、
对象行为与玩家取得边界均可由同一 catalog 证明的完整 family。

## 2. Source-object catalog

### 2.1 范围

R0 的 cohort A 预期使用 119 个 GT6 source identities：17 个 stone material identity，
每种保留 full block 与 6 个 slab variant。catalog 必须从 source identity 投影，不按
`metadata` 连续区间、显示名称或 item id 猜测成员：

```text
gregtech:gt.stone.<stone>
gregtech:gt.stone.<stone>.slab.<variant>
```

它们代表真实、可区分的建筑/石材对象。每一个 catalog entry 至少记录：

```text
source item identity + source location/revision
canonical CC block and BlockItem id
stone family + slab variant
blockstate/model/loot/tag assets
creative-tab visibility
survival acquisition or deterministic source-backed conversion
runtime registry identity and source-to-runtime equivalence proof
```

### 2.2 实现边界

新增 `GtStoneCatalog`（或同等数据源）和其注册/数据生成投影。它必须产生真实
`Block`/`BlockItem`，并分别保留 full block 与 slab 行为；禁止注册同名无方块行为 item、
无来源 crafting token，或把所有 source slab 折叠为一个 stone item。

可复用 T41 `GtWoodCatalog` 的 “catalog → registry/creative/datagen/lang → B0 evidence”
模式，但不得复用其木板语义或 fireproof component。T43 的 catalog 只允许以下两种
source-backed 玩家取得边：

1. 对应 CC stone 的 worldgen/drop/采集路径已经在 B0 中有可审计来源；
2. 本卡为该 catalog entry 新增显式、有限且 source-backed 的 conversion/drop 路由，
   所有输入必须在 B0 可达并计入 publication/load delta。

创意栏可见、注册成功、GameTest 注入或 namespace allowlist 都不是玩家取得证明。

### 2.3 不扩张的对象范围

catalog 的 119 identities 不自动承诺：

- GT 的其他 `gt.stone.*` 家族、楼梯、墙、装饰物或未被 T43 source relation 消耗的变体；
- hazmat armor、storage meta item、MTE、food、tool head、植物、矿物 prefix；
- source material 的所有 dust/plate/molten form；
- 石材的整套 worldgen 重做。

任何新增对象均须来自 T43 production lock 的 relation operand，或另开有 owner 的 card。

## 4. R1：recipe publication 与数据驱动 policy

T43 使用 exact singleton compact relations。生成树和测试 fixture 必须严格隔离：

```text
src/t43_recipe_generated/resources/data/cruciblecraft/recipe/t43/smelter/
src/test/resources/t43_catalog_fixture/data/cruciblecraft/recipe/t43_catalog/
```

在生成前将 publication group 和 materialization policy 置于受 schema 校验的 manifest，
由 `GTRecipeMapLoader` 通用加载，而不是为 T43 新增一个 hard-coded Java 常量/白名单分支。
manifest 的每个 group 应至少声明：

```text
target_map
publication_group
family/relation membership root
policy type, cache and eager selector
router schema/version
group and aggregate hashes
```

T43 policy 只能在 policy-before-measure 后由实测选择。默认不得复制 T37/T39/T40/T41
的 eager/lazy/cache 比例。新的 loader manifest 层必须保留：

- 未声明 `(target_map, publication_group)` fail closed；
- cross-group authored/stable/logical identity collision fail closed；
- 旧 group 与 T43 group 同 target 原子 reload；
- `ComponentIngredientIndex` 无法索引的 relation 进入显式 overflow，而不是回退全
  Smelter scan。

`CompactRecipeShardRouter` 的 query-visible item、fluid、component 与 input-shape keys
负责拆 shard；不能按文件序号、stable id hash 或每 128 行盲切。所有 shard 和 overflow
都须满足现有 128 candidate hard ceiling。

## 5. R2：玩家路径、执行与等价

T43 的分层闭包为：

```text
B0 = T42 cumulative typed closure，不含 T43 production/support
B1 = B0 + T43 production-lock-owned minimal stone acquisition support
B2 = B1 + 407 T43 Smelter relations
```

若 catalog entry 的 source-backed 取得已在 B0，不能为凑形式添加 support。反之，support
只可补 production lock 反向依赖中的有限 acquisition 边，且所有 support input 要在 B0
可达、support output 要是已注册 catalog identity。T43 production/support tree 禁止进入
B0，防止 self-certification。

验证必须同时覆盖：

1. Python source → generated：407/407 relations 的全字段等价；
2. Java codec/provider/loader：真实 generated root、每个 publication group、stable id、
   shard membership、router positive/negative lookup、no-shadow；
3. Runtime：server、dedicated client、reload、EMI、machine execution success/reject 与
   runtime fingerprint 一致；
4. object：full block/slab 的 state、model、loot、pick/drop、creative visibility 和
   source-backed survival acquisition；
5. GameTest：所有 relation 由 data-driven harness 覆盖，isolated `cruciblecraft_t43`
   suite 只抽代表 execution/reload/EMI，不以样本代替 relation-level equivalent test。
