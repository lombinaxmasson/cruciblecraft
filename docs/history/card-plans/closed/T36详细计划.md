> 性质：机器基础设施与内容实现卡；闭卡后执行一次 delta census 和后续拓扑重签发

> 前置：T35/T35R 的底层 census 分母可复用，但其 1.x scope 投影与 T38–T46 storage-only 拓扑已撤回
> 后继：T37 ordinary-optional Assembler 校准与通用 compact family 底座（当前唯一 active）；
> 其后依次为全量配方缺口轨、storage 轨和 1.x 退出门

## 0. 先读这一节

### 0.1 为什么重写 T36

当前 33 variants / 11 kinds 只是已经实现的 opening，不是 1.x 机器目标分母。T35R 错误地
用这 33 行定义 selected matrix，再由“当前行均已存在”推导：

```text
generated_material_cards_required = false
generated_eu_cards_required = false
```

这个结论是循环定义，不能证明原 roadmap 宣布的机器等级轨已经完成。它进一步导致：

- 未实现机器 host 被自动判为 `post_1x` 或 `out_of_scope`；
- 依赖这些 host 的 ordinary recipe family 被排出 1.x；
- T38–T46 只剩 storage cards；
- P0/P1/P2/P3 从开发顺序错误变成了版本范围。

T36 必须先建立独立于当前实现的目标分母，再完成该分母中的全部 1.x 机器样式。只有
`target - runtime = 0` 后，才能重新签发 machine conclusion A。

### 0.2 本卡对 T35 的处理

保留并复用：

- 8,996 identity 总目录；
- T13 七表 765 identities；
- exclusion 763 source sites / 1,701 expanded registrations；
- runtime expected/mapped 20,553 的 opening；
- ordinary-optional 78,682 rows / 5,718 families；
- Storage 28/624 与 logistics 1/1；
- T14 load axis、compact/full-replay 分层和验证基础设施。

撤回并重算：

- 由优先级自动派生的 `portfolio_scope`；
- “33 行即完整机器目标”的 conclusion A；
- missing-host recipe 自动 `out_of_scope`；
- bath/smelter/mixer 自动 `post_1x`；
- T38–T46 storage-only topology。

历史 T35 计划、工作日志和阶段档案保持只读。当前 overlay 通过 T36 delta 和新的 topology
epoch 修正，不改写历史闭卡叙述。

### 0.3 一句话判据

> 先从 pinned GT6 machine rows、1.x ordinary-recipe host 需求和 roadmap 宣布轨道建立独立
> machine target；再让一个 canonical catalog 无损投影全部目标 machine variant 的注册、
> 资源、acquisition、能源语义、运行时行为和存档 identity；最后证明 target、catalog 与
> runtime 三集合相等，并基于 post-T36 host availability 重算 recipe scope 和 T38+ 拓扑。

## 1. 固定产品决策

### 1.1 “全部机器样式”的边界

T36 的“全部”指：

1. 1.x ordinary-optional 5,718 families 所需的全部 CC-owned machine hosts；
2. roadmap 已宣布的 RU、KU、HU source-backed material variants；
3. roadmap 已宣布的 EU voltage variants；
4. TU/TIME identity 所需的实际 host kinds；
5. 以上 host 的 acquisition、表现层、菜单、block entity、保存与最小可运行路径。

它不表示自动移植 GT6 的全部对象。下列内容只有在成为上述机器/配方闭包的真实前置时才进入：

- 裂变、聚变、等离子和反应堆专用机器；
- 外部模组兼容能源与 wrapper；
- 尚未进入当前产品范围的 multiblock/controller 系统；
- 纯装饰、debug、creative-only 或无玩家路径对象。

任何排除必须记录 canonical id、source row、排除理由和后续阶段；不能因为当前 Java 中没有
实现就自动排除。

### 1.2 priority 不决定版本范围

- `portfolio_scope` 回答 1.x 是否承诺关闭；
- P0/P1/P2/P3 只回答实施顺序、风险和适合的表示方式；
- `disposition` 回答当前是 implemented、planned、deferred 还是产品排除；
- load budget 决定 batch、compact/lazy 策略和缓存方式，不自动把 family 推到 `post_1x`。

所有 CC-owned、source-backed 且属于 1.x 配方闭包的 machine/recipe identity 都是
`in_scope_1x`。缺 host 是依赖关系，不是产品排除理由。

### 1.3 当前 33 行只是 opening

现有 33 rows / 11 kinds 必须逐行保留：

- stable runtime id；
- source id、source tier 与 source row；
- material、energy identity、tier/voltage band；
- input window、capacity、parallel、efficiency、overclock；
- block/item identity 与已有存档兼容。

但所有 `== 33`、`must remain 33`、固定 11 kind 枚举和 T16/T17 历史批次常量必须从当前
运行时目标契约移出。历史测试可继续验证 opening，不得限制新目标行。

### 1.4 三类机器分母

三类分母分别建模，禁止混写：

1. **Material variants**
   - RU、KU、HU；
   - 只消费 pinned source 中真实存在的 `kind × material` 行；
   - 禁止自动笛卡尔补全。
2. **EU voltage variants**
   - voltage band 是执行/保存语义，不是材料等级；
   - material 只记录外壳、acquisition 或 source identity；
   - 必须覆盖 1.x recipe host 所需 EU kinds，不局限于当前 electrolyzer 三行。
3. **TU/TIME hosts**
   - 不进入 `machine_tiers.json` 的 material matrix；
   - 独立枚举 Autoclave、Bath、Coagulator、Generifier 等 source hosts；
   - 每个 host 独立给出 implemented/planned/excluded 与理由；
   - Coagulator 不能仅因当前未注册而自动 `post_1x`。

### 1.5 T38–T46 为 provisional

当前 T38–T46 全部 `started=false`，且来自已撤回的 scope 投影。T36 授权在闭卡时创建新的
topology epoch：

```text
T36 machine closure
  └─ T37 ordinary-optional calibration
       └─ recipe closure waves
            └─ storage implementation bundles
                 └─ 1.x exit gate
```

固定节点 T36、T37 不重编号。旧 T38–T46 不具有 append-only 保护；新 epoch 签发后再冻结。

- 每个 family 使用的 source RecipeMap；


### 2.3 Target freeze gate

- target kind count；
- material/EU/TU 各自 row count；
- source row set；
- required RecipeMap/family coverage；
- 显式排除集；
- opening 33 rows 与新增 rows 的差集。

这些数字在计划中不预填。builder 复算前保持 `null`，禁止先决定“只有 33 行”再让实现适配。

## 3. Canonical catalog 与注册架构

### 3.1 单一数据源

`machine_tiers.json` 升级为完整 machine variant catalog，或由等价的新 canonical catalog
替代。Java 中不得再维护第二份 kind/variant 列表。

catalog 负责投影：

- processing behavior/kind；
- block 与 item；
- block entity 与 menu；
- creative tab；
- blockstate、block model、item model；
- language；
- loot 与 acquisition；
- EMI/workstation；
- runtime/census identity。

Java 只保留行为实现、类型安全 adapter 和必要的特殊 controller，不复制 variant rows。

### 3.2 移除固定 opening 限制

至少处理：

- `MachineTierCatalog` 的 `variants.size() == 33`；
- `ModMachineVariants` 的 11 个静态 kind 常量与手写 `KINDS`；
- T16/T17 selected 常量对当前总目录的所有权；
- block/item/datagen/creative tab 中按 variant 重复的注册；
- 测试中把 33/11 当作未来 hard ceiling 的断言。

opening 断言迁入历史兼容测试：

```text
existing 33 ids remain present and semantically equal
```

current 断言改为：

```text
catalog ids == target ids == runtime ids
```

### 3.3 稳定 ID 与迁移

- 已有 tier-1 bare id 保持不变；
- 已有 33 ids 不改名、不复用；
- 新 variant 默认 `<material>_<kind>`，EU/TU 若无法用该规则准确表达，必须在 target
  contract 中声明 naming policy；
- block entity 保存 variant id，不依赖 registry 顺序或数组下标；
- 旧存档读取、未知 id 和移除 id 必须 fail closed，不静默换成另一台机器；
- item placement、pick block、clone stack 与掉落保持同一 variant identity。

## 4. 样式、资源与玩家路径

每个 target variant 必须同时闭合以下表面：

### 4.1 注册

- block；
- item；
- block entity type；
- menu/type；
- creative visibility；
- server/client registration；
- census runtime id。

### 4.2 表现层

- blockstate；
- inactive/active model 或明确无 active state；
- item model；
- material/casing tint；
- front/back/side/top/bottom 方位；
- active overlay；
- language；
- 不存在错误复用、方向错位、空 texture 或 `ART_MISSING`。

允许多个 variant 共享参数化模型和 texture profile，不要求复制 PNG。共享必须由 catalog
显式声明，不能靠文件名偶合。

### 4.3 Acquisition

- 每个生存可用 variant 有 recipe、升级路径或明确 source-backed 获取方式；
- tier progression 不形成环；
- 高阶材料在使用前可获得；
- creative-only 只允许产品策略明确声明的对象；
- acquisition 输出进入 reachability/current census。

### 4.4 运行语义

- 接受正确 energy identity；
- input min/nominal/max 和 capacity 来自 source 或明确设计政策；
- EU 欠压、正常电压、过压和 overclock 行为有独立测试；
- material tier 与 EU voltage 不混用；
- parallel、parallel-duration、efficiency、cheap/standard overclock 精确投影；
- recipe host 与 RecipeMap 一致；
- GUI、progress、槽位和 sided capability 与 kind 行为一致。

### 4.5 最小可运行性

T36 不批量实现 ordinary recipe long tail，但每个新 host 必须满足以下之一：

1. 已有至少一条可达、可执行的非校准 recipe；
2. T36 增加一条有界 bootstrap recipe，并单独记录 publication delta；
3. 该 host 明确是 T37 后 recipe wave 的前置，且不向玩家注册不可用的空机器。

禁止仅注册方块、没有 acquisition、没有能源路径、没有任何 recipe 的“目录完成”。

## 5. T36 内部实施波次

这些是同一张 T36 的内部里程碑，不分配新的 T 卡号。

### R0 · Target freeze

- 构建 `t36_machine_target.json`；
- 从 source rows 与 recipe host 需求得出真实目标；
- 分开 material、EU voltage、TU host；
- 输出 opening、target、missing 与 excluded 集；
- 人工审阅 target/exclusion 后才进入实现。

### R1 · Catalog schema

- 升级 schema；
- 移除 33/11 current hard limit；
- 建立 kind、variant、resource profile、acquisition 与 persistence 字段；
- 保持 opening 33 行字节语义等价。

### R2 · Registry projection

- 让 block/item/block entity/menu/creative tab 从 catalog 投影；
- 删除重复、错位和按批次复制的 variant 注册；
- 保留特殊行为 adapter，但不保留重复 variant 数据。

### R3 · Datagen 与表现层

- 从 resource profile 生成 blockstate/model/item/lang/loot；
- 修复现有资源方向错位和错误复用；
- 为新增 target variants 建立完整资源路径；
- 连续双跑 datagen，第二次生成树零变化。

### R4 · Material variants

- 按 source row 实现 RU/KU/HU target；
- 不做笛卡尔补全；
- 每完成一个 energy family，运行 identity、resource、acquisition 和 behavior gate。

### R5 · EU voltage variants

- 独立迁移 EU voltage 语义；
- 实现 target 中全部 EU hosts/voltage rows；
- 验证电压、overclock、保存与 acquisition；

### R6 · TU/TIME hosts

- 枚举并实现 target TU hosts；
- 单独裁决 Autoclave、Bath、Coagulator、Generifier；
- 不写入 material matrix；

### R7 · Runtime equality 与 persistence

- target ids == catalog ids == block ids == item ids；
- block entity/menu/datagen/creative tab 无漏项；
- opening 33 id 与行为保持；
- 新旧 variant 保存、加载、放置、掉落与网络同步通过。

### R8 · Post-machine delta census

新增：


delta 必须记录：

- opening 与 closing runtime ids；

## 6. Post-T36 scope 与拓扑规则

### 6.1 Recipe scope

T36 关闭后：

- 所有 CC-owned、source-backed、host 可用的 ordinary family 为 `in_scope_1x`；
- T37 的 50 assembler families 仍由固定卡 T37 所有；
- 其余 family 按依赖和实现成本分 wave，P0–P3 只控制顺序；
- bath、smelter、mixer 等大分母不得只因规模大转为 `post_1x`；
- 需要 compact/lazy 表示时，先生成架构前置或 calibration bundle；
- missing host 只允许在 target 明确排除或依赖未来核能/兼容系统时不进入当前配方轨。

### 6.2 Track 顺序

新 topology 必须表达：

```text
T36 complete
T37 calibration
recipe host/foundation prerequisites（若 R8 仍发现）
bounded recipe waves，直到 1.x recipe gap 为零
storage implementation bundles
1.x exit gate
nuclear source/physics census
```

Storage 不得排在未关闭 recipe wave 前。九个 canonical storage family 不要求一族一张卡；
应按共享 runtime 架构、行为、资源和 load boundary 合并成可审查 bundle。

### 6.3 Topology reset

- 旧 T38–T46 全部未启动，因此允许撤销；
- 新 topology 从 T38 重新连续编号；
- T36/T37 固定不变；
- 新 epoch 签发后才启用 append-only；
- 任何 card 必须有 owner、依赖、replacement/recheck、load opening 与 exit gate。

## 7. Load 与规模纪律

T36 会增加真实运行时内容，不能继续声明 `publication_delta = 0`。必须分别计量：

- block、item、block entity type、menu type；
- eager/lazy/logical recipe publication；
- model/blockstate/lang/loot entries；
- creative tab rows；
- machine catalog rows 与 runtime indexes；
- server startup、resource reload、memory、sync payload；
- EMI recipe/workstation registration；
- datagen tree size。

规则：

- T14 hard ceiling 不因“全部机器要放下”而提高；
- 超 soft budget 时优化共享 resource profile、registry projection、lazy index 或 batch；
- 不用删除 target row 伪造预算通过；
- pending 不填 0；
- 每个内部 wave 记录 opening + delta + closing；
- 最终 closing 必须低于 hard ceiling。
