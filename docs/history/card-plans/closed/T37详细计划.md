## 0. 先读这一节

### 0.1 固定范围

T37 不重新选样，也不按实现方便调整范围。唯一 work set 为：

```text
host = cruciblecraft:assembler
owner = portfolio:track_a/t37_pilot
families = gt.recipe.assembler#0002 ... gt.recipe.assembler#0051
family_count = 50
source_rows = 50
expanded_rows_per_family = 1
```

完整 canonical id 由 `tools/t35_census.json#t37_pilot` 与
`tools/t35_recipe_families.json` 交叉派生；builder 必须验证连续的 `#0002`–`#0051`
恰好 50 项，禁止在计划或代码中维护第二份手写清单。

`#0000` 与 `#0001` 分别是 620 / 619 行的大 family，不属于 T37。其余 Assembler
family、T38 的 29 个 Roaster family、其他 ordinary_optional、storage 与后续核能轨均
不属于本卡。

### 0.2 为什么 T37 不是“手写 50 条 JSON”

这 50 个 family 都是 singleton，生产结果可能最终表现为 50 条精确 recipe，但来源、
映射、生成、等价证明和载荷账目必须由同一条可重放管线生成。T37 要证明的是：

```text
pinned GT6 source row
  -> reviewed compact source
  -> generated datapack family entry
  -> runtime RecipeMap relation
  -> player-visible execution and EMI enumeration
```

任何一步都不得依赖复制粘贴、文件存在、注册数量或另一个 family 的压缩比例。

### 0.3 通用底座决策

T37 同时建立后续长尾波次可复用的 host-neutral compact family 底座，而不是再复制一个
Assembler 专用版 `ExtruderRecipeFamilyProvider`。

底座只在 T37 实现并验证 **exact relation** 能力，同时预留参数化 definition 的扩展点。
Bath、Mixer、Smelter 等大 family 的实际参数模板不在本卡实现；它们后续通过同一 provider
接入，不要求 T37 提前猜测所有模板形状。

现有 `MaterialRule.SparseTable` 是 Extruder 专用合同，包含 shape、material、forging 与
`extruder/` stable-id 约束。T37 禁止把任意 Assembler row 强行伪装成 Extruder sparse
relation，也不因抽取通用代码而改变 T14 Extruder 的 20 authored / 2,782 logical /
557 eager / 2,225 lazy / 512 cache 既有行为。

### 0.4 一句话判据

> 从 pinned GT6 dump 无损冻结固定 50 个 Assembler singleton family，由批量编译器生成
> host-neutral compact family 资源，在真实 RecipeMap、客户端枚举和玩家执行路径中证明
> 逐字段等价；用实际 50-row workload 比较 immediate、on-demand 与 hybrid，按预先冻结
> 的决策规则选择生产策略，并把 T36 closing 到 T37 closing 的全部 T14 轴写入可重放账目。

## 1. 固定产品与证据决策

### 1.1 三个独立验收轴

1. **Closure**
   - 50 个 family 全部有唯一 compact source、生成资源与 runtime stable id；
   - 全部输入可获得、输出可消费、Assembler host 可执行；
   - source / generated / runtime / EMI 集合相等。
2. **Fidelity**
   - 每条 row 的输入、输出、数量、输入动作、概率、duration、EU/t、special value、
     buffering 与顺序来自固定 source；
   - `SOURCE_BACKED`、`SOURCE_DERIVED`、`DESIGN_POLICY` 分开记录；
   - 任何无法映射的 source 字段是 blocker，不得静默丢弃。
3. **Load**
   - 每个 family 独立记录 source/authored/logical/eager/lazy；
   - card 级记录 cache、sync、reload、index、memory、allocation 与 lookup；
   - 正常选择不得越 soft budget，hard ceiling 不得提高。

### 1.2 来源重放规则

本卡的 write/review 与闭卡必须具有本地：

```text
gt6_dump/gt6_recipe_dump/maps/gt.recipe.assembler.json
```

并验证固定 revision、文件 hash、enabled membership 与 T35 family 分组。缺少 raw dump 时：

- 普通 compact currentness 可以验证已提交 receipt；
- explicit source-replay 必须报告 `SKIP` 或 actionable failure；
- 首次生成、来源变更和 T37 闭卡不得把 `SKIP` 写成 replay 通过；
- 不允许从 T35 的 `expanded_count = 1` 反推 recipe 内容。

完整重放后提交 compact source 与 hash receipt，使普通 CI 不依赖 gitignored dump。

### 1.3 精确字段合同

每条 source relation 至少固定：

```text
family_id
source_map
source_recipe_index
source_revision
source_row_sha256
stable_id
target_map
item_inputs
item_input_counts
item_input_actions
item_outputs
fluid_inputs
fluid_outputs
output_chances
duration
eut
special_value
can_be_buffered
shadow_order
provenance
```

Source 中的 disabled、hidden、fake、空 slot、容器返回、催化剂或工具磨损语义必须先显式
分类。CC runtime codec 无法等价表达的字段不得简单删掉；应扩展合同或阻断该 row。

### 1.4 映射与玩家路径

每个 item/fluid operand 必须得到以下之一：

```text
exact_runtime_id
registered_material_form
canonical_tag
source_derived_alias
blocked_unmapped
```

`blocked_unmapped` 不能进入生成资源。输入需通过 acquisition/reachability 图；输出需在
runtime registry 中存在并可由 EMI 显示。创造模式注入只能用于隔离执行测试，不能替代
生存获得性证明。

### 1.5 T37 校准边界

50 个 singleton family 只能证明：

- exact-row 编译与发布的固定成本；
- 多 family 同 host 的索引、缓存、同步与枚举行为；
- 50-row 规模下三种 materialization strategy 的实际成本。

它不能证明：

- 620/619-row Assembler family 的压缩比例；
- Bath 1,116-row family 或 Mixer 多轴模板的成本；
- 所有后续波次都应使用 T37 的 eager/lazy 比例。

T38+ 必须继续对自身 family 重新测量，禁止把 T37 ratio 套到其他分布。

Builder 负责：

2. 从 `t35_recipe_families` 验证 host、classification、template key 与 singleton count；
3. full replay Assembler dump，恢复准确 source index 与 row；

### 2.2 Stable id

Runtime stable id 必须由 source revision 下稳定的 family id 与 row fingerprint 派生，不得
使用生成顺序、当前 registry index 或易变路径作为唯一身份。

输入顺序打乱不得改变 stable id；source recipe 顺序变化但内容不变时，builder 应保持
identity 并单独报告 source index drift。

### 2.3 人工审阅点

R0 在生成 runtime 文件前输出审阅摘要：

- 50 rows 的 item/fluid slot shape 分布；
- fixed id、material form、tag 与 alias 数量；
- catalyst/tool/container action 数量；
- chance output 与 special value 分布；
- unmapped operands、unsupported semantics、input shadow 候选；
- 每条 row 的玩家 reachability。

任一 unmapped 或 unsupported 不得靠默认值进入 R1。

## 3. R1 · Host-neutral compact family codec

### 3.1 新 recipe source 类型

计划新增 host-neutral compact family recipe envelope，命名在实现时固定为单一 canonical
类型，例如：

```text
cruciblecraft:compact_gt_recipe_family
```

每个 authored family entry 至少包含：

```text
family_id
target_map
source_revision
relations[]
```

Relation 使用轻量、可同步的资源定义和 stable id，不在 lazy definition 层预先保留完整
`GTRecipe` 对象。只有 eager publish、lookup hit 或完整 enumeration 时才解析为
`RecipeMap.Entry`。

### 3.2 计划 Java 边界

预计新增或抽取：

```text
CompactGTRecipeFamilyEntry
CompactGTRecipeFamilyDefinition
CompactRecipeFamilyProvider
CompactRecipeFamilySource
```

预计修改：

```text
ModRecipes
GTRecipeMapLoader
RecipeMap
GTRecipeMapClientEvents
PublicationMetrics
```

最终类名可在 R1 固定，但职责不可混写：

- codec 只负责数据合同；
- provider 只负责 epoch snapshot、索引、materialization 与 cache；
- loader 负责按 `target_map` 聚合 source 并原子发布；
- `RecipeMap` 继续拥有 lookup/enumeration 合同；
- load/readiness builder 只读取测量，不在 JSON 中伪造 runtime 结果。

### 3.3 Host-neutral 门

通用实现必须满足：

- 不含 `ASSEMBLER` 常量分支决定核心行为；
- 可对任意已注册 `RecipeMap` 建 snapshot；
- 未知 target map fail closed；
- 测试至少使用 Assembler 与一个 synthetic second map，证明不是主机特例；
- 同一 map 可同时拥有 concrete base entries 与 compact families；
- 与现有 Extruder family 共存，但 T37 不要求迁移 Extruder。

### 3.4 Definition 与索引

Provider 至少支持：

- item identity / tag ingredient；
- string component ingredient；
- fluid identity；
- `CONSUME`、`PRESERVE`、`WEAR`；
- 多 item/fluid 输入输出；
- chance output；
- stable-id lookup；
- item/component/fluid candidate index；
- 完整 enumeration。

无法索引的 relation 必须明确进入 bounded unindexed 路径并计数；不能因候选少而漏配方。

### 3.5 Epoch 与客户端

- reload 先构造完整 candidate snapshot，全部校验通过后一次 publish；
- reload 失败保留旧 epoch，不发布半成品；
- cache 绑定 epoch，reload 后旧 cache 不可见；
- integrated client 复用 server snapshot，不重复构建；
- dedicated client 得到相同 recipe ids 与 stable fingerprint；
- enumeration 不允许预热或无限增长 lazy cache；
- sync payload、reload 与 index 时间进入 T14 ledger。


   - Assembler map 精确增加 50 logical ids；
   - 全量 enumeration 与 expected ids、fingerprint、字段相等；
   - 无 duplicate id、input shadow、missing index 或 cache-dependent enumeration。

## 5. R3 · Materialization candidates 与选择

### 5.1 三个候选

同一批 50 relations 实测：

```text
immediate
on_demand
hybrid
```

禁止复用 Extruder 的 `HOT_MODULO = 5`、512 cache 或历史 20x 比例作为 T37 结果。
Hybrid eager subset 与 cache ceiling 必须由 T37 policy 在测量前声明候选值。

### 5.2 测量规模

- 生产判定只使用 actual 1x = 50 logical rows；
- 5x / 20x 可以作为诊断压力样本；
- 不从 5x/20x 比例推导 1x 未测字段；
- `recipe_load_projection` 中 production `logical_rows` 必须出现在
  `measured_logical_rows`。

### 5.3 预先冻结决策规则

在运行 benchmark 前提交 candidate policy，至少规定：

1. 字段等价、完整枚举、客户端一致与玩家执行先通过；
2. 任一 hard ceiling 失败即淘汰；
3. 正常生产候选必须位于累计 soft budget 内；
4. 不把不同单位加成一个无来源的综合分数；
5. 在均通过时按预先声明的优先序比较 eager margin、retained memory、
   reload/index、lookup、sync 与实现复杂度；
6. 选择结果由 builder 从原始测量派生，不能手填。

50-row immediate 很可能足够，但计划不预先宣布胜者。选择 immediate 时，lazy/cache
明确为实测零；选择 on-demand/hybrid 时，provider 必须证明完整 enumeration 与 bounded cache。

### 5.4 Benchmark 工件

计划新增：

```text

```

单次样本替代 p50/p95 interval。

## 7. R5 · 玩家路径、执行与表现

### 7.1 Reachability

每条 recipe 的全部 consumable input 必须从已有 S(k) acquisition graph 可达。PRESERVE/WEAR
输入必须具有对应工具/催化剂获得路径。输出必须：

- 有后续消费、存储或明确终端用途；
- 在 EMI Assembler category 可见；
- 不依赖 creative-only placeholder。

### 7.2 Runtime 行为

数据驱动 Java harness 对全部 50 relations 验证：

- matcher 接受精确输入并拒绝缺失/错误输入；
- consumption action 正确；
- chance、duration、EU/t、special value 与 buffering 正确；
- machine capacity 与 T36 Assembler variant 至少有一条可执行路径；
- reload 前后 stable id 与结果一致。

隔离 GameTest namespace 计划为：

```text
cruciblecraft_t37
```

GameTest 至少覆盖：

- 50-row publication 与完整枚举；
- dedicated runtime Assembler 实际执行；
- player-obtainable representative paths；
- reload/epoch/cache；
- EMI 计划与 runtime ids 一致。

静态 reachability 覆盖全部 50；代表性世界测试不能替代全量 matcher/execution harness。
