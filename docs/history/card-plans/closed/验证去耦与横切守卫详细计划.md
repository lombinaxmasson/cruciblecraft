## 1. 现状（盘点摘要）

`capability-runtime` profile：64 个 Python 模块 + 30 个 builder，每次 push 全量跑（CI 里唯一没有
`--if-changed` 的 profile）。本地 94/94 通过，总耗时约 4 分钟。成本不在时间，在耦合：

| 失败模式 | 规模 |
|---|---|
| 同一份 `identity_resolution_ledger.json` 的 sha256 复制在 33 个 `baseline_ledger_sha256.txt`；R0 disposition 同样 33 份 | 约 14 个 builder + 12 个测试检查它们 |
| 断言工作流状态（unique_active、plan 在 active/closed、"X stays unimplemented"） | 52 个模块、27 个 builder |
| 断言 Java 源码文本（`"INTERVAL = 5"`、`"BASE_Y = 40"`） | 33 个模块、24 个 builder |
| 测试里再调一次 builder 的 `check()`，与 builder 步骤重复 | 31 个模块 |
| 按别的卡的文件在不在切换断言 | 10 个模块、20 个 builder |
| 实际读 gitignored `gt6_code`（CI 没有这棵树） | 7 项；`gt_stone_layer_rocks` 已确认会在 CI 上悄悄跳过 |

另有一条相关现状：106 张声明了 `required_test_ids` 的 capability 里，只有 73 张通过
`player_complete.check_declared_test_ids`。其余 33 张多数是"声明集合是 owned 文件里测试的子集"
（多卡共用 GameTest holder），少数 discovered 为空，因为测试已迁到 `src/test/java`
或本来就是 JUnit，但 owned_paths 没跟上（例如 `machines/large-shredder`、`machines/large-sluice`、
`registry/prefix-material-component`）。换句话说，这 33 张卡的"required 测试必须存在"现在实际上没人执行。

## 2. In scope（按阶段，每阶段独立合入）

### A. 去掉共享哈希钉

1. 删掉 14 个 builder 模块里对 `R0` / `LEDGER` 的 `_sha256` 比对，以及 `write()` 里写 sha 文件的代码。
2. 删掉 66 个 `r0_disposition_sha256.txt` / `baseline_ledger_sha256.txt`。
3. 删掉测试里的 `r0_and_baseline_hashes_are_pinned`、`r0_and_baseline_ledgers_are_untouched` 这类断言。
4. VD-2026-09-004（`test_display_cpu` 的 `PINNED_*_HASH`）按同一规则处理：钉本卡拥有的行或结构不变量，
   不钉共享文件的整文件哈希。完成后关闭该债务行。
5. 若某张卡确实需要保护自己拥有的账本行，改为比对这些行的结构，不比对整文件字节。

这与 `docs/current/verification.md` 现行政策一致（不把文件摘要接回日常证明），不是放松。

### B. 通用 required-test 检查

1. 合同从"声明集合 == owned Java 文件里的 `@GameTest` 集合"改为：
   - 每个声明的 id 都能在 `src/test/java` 或 `src/main/java` 找到对应的 `@GameTest` 或 `@Test` 方法；
   - 声明内部无重复；
   - 同名方法出现在多处时报出来，由人决定。
2. 一个常驻测试对全部 capability 跑这条合同，复用 `tools/player_complete.py` 的发现逻辑。
3. 先修现有 33 张不一致的卡：多数只是合同改了之后自然通过；真正找不到方法的，列出来，
   在该卡的 capability 里修 `required_test_ids` 或 owned_paths，不在本卡补写测试。
4. 之后删掉各卡测试里逐条的 `"missing GameTest X"` needle 和 `required_game_tests_exist` 一类测试。

### C. 横切守卫收成全仓库 lint

每条一个模块，扫描整个仓库，而不是只看某张卡；每条都带一个反例 fixture，证明违规时会失败：

1. **美术不许别名**：art manifest 的目标文件必须存在；不许指向 `multiblock_casing`、`pipe_filter_cover`
   等已知替身；来源必须在 `gregtech6_w` 路径下。取代约 15 个模块里各自的 `art_is_copied_and_not_aliased`。
2. **配方不许替身**：已知替身形态（单个 `programmed_circuit` 顶电路、plate 顶 curved/double plate 等）
   在 live 配方里出现即失败，除非来源行确实是它。取代 `player_complete_forbids_recipe_stand_ins`（4 份）、
   `blank_recipe_is_not_faked_with_programmed_circuit` 等。
3. **不许 catalog 撒点**：live 代码与 worldgen 里不许出现已退役的 scatter feature / ItemEntity 撒点，
   数量必须为 0。先核对 `test_player_complete.test_catalog_item_entity_worldgen_is_forbidden_obtain`
   已经覆盖了多少，不重复造。
4. **不许引用已撤回的 dummy id**：live 配方与 tag 里的 id 必须是已注册 id。

规则：每条 lint 在当前树上先跑一遍。如果它抓到真实违规，把违规登记为 blocked / debt，
**不在本卡修内容**；lint 先用显式 allowlist（带 blocker id）挂上，allowlist 只减不增。

### D. 降级与重新分组

按盘点表逐项处置（下面是汇总，逐项见盘点文档）：

| 去向 | 模块 | builder |
|---|---|---|
| 挪到 `verification` profile（测 Python 工具本身，工具改了才跑） | 7：capability_ledger、project_status、capability_close、blockers、material_form_demand_census、registry_identity、jade_source_mapping | 3：blockers、capability_ledger、project_status |
| 留在 capability-runtime（加 `--if-changed`） | C 阶段新建的 lint + B 阶段的通用检查 | jade_observation、catalog_modern_ids、registry_identity |
| 仅 release | — | gt6_full_coverage（76 s，全局报告） |
| `manual_replay` | 其余约 55 个 | 其余约 23 个（E 阶段拆分后部分回到 if-changed） |

- `python_test_policy.json` 里对应模块标为 `manual_replay`；文件与测试方法都保留。
- 降级前，每个模块必须在当时的 revision 上通过一次；不许把红着的测试降级来"变绿"。
- `.github/workflows/build.yml` 的 capability-runtime 步骤加 `--if-changed`。
- 顺带处理 VD-2026-09-001（capability affected_rule 一锅炖）：降级后这条规则只剩 lint 和通用检查可选，
  拆成按路径选择。

### E. 拆分生成类 builder（并入本卡，单独合入）

约 12 个 builder（gt_trees、gt_crops、gt_stone_layer_rocks、gt_small_ores、pipe_cable_baseline、
connector_art、foundry_art、storage_art、mte_inplace_runtime、paper_tiny_plate、
technological_parts_foundation 等）的 `check()` 里混着三样东西：

- 生成输出与生成器一致（有价值，保留，按输入 `--if-changed`）；
- Java 源码文本 needle（删掉；行为由同卡 GameTest 证明）；
- 工作流状态 / 别卡文件探测（删掉）。

动手前逐个确认它们是否真的写 `src/` 下被游戏读取的资源；盘点里的判断来自路径特征。

### F. 本地与 CI 一致

- 常驻 CI 的检查不许读 gitignored 参考树（`gt6_code`、`gt6_dump`、`gregtech6_w` 等）。
- 需要参考树的检查只能是 `manual_replay`，或在缺树时**显式报告 SKIP 并说明原因**；
  不许用 `if path.is_file():` 悄悄跳过。
- 现有 7 项逐个处理：`test_gt_stone_layer_rocks`、`test_catalog_modern_ids`、
  `test_gt6_connector_acquisition`、`test_material_form_demand_census`、
  `build_catalog_modern_ids`、`build_gt_stone_layer_rocks`、`build_gt6_connector_acquisition`。

## 5. 决定（2026-09-29 用户确认）

1. **manual_replay 在 release 里：跑，只报告，不挡发版。**
   `verify.py release` 增加一个 manual_replay 报告段：逐模块 PASS / FAIL 写进
   `build/verification/latest.json`，FAIL 不改变 release 退出码，但必须在输出里列出。
   这属于 D 阶段范围，owned path 增加 `tools/verify.py`（只加这一段，不改路由）。
2. **E 阶段并入本卡。** 本卡 A–F 全部完成才关。
3. **本卡占 unique-active，并且由工具强制。**
   capability 在 `tools/capabilities/tooling/verification-decoupling/capability.json`：
   `maturity=frozen`、`workflow=active`、`survival_access=not_applicable`、`profiles=["verification"]`。
   ledger 的 `unique_active_slug` 由此推导。关卡时计划挪到 `closed/`，capability 改 `accepted`。
   本卡关闭前不开新的内容卡落地。这改变了"验证卡不建 capability"的前例，是有意的：
   锁要由 `compile_ledger()` 守，不靠文档提醒。
