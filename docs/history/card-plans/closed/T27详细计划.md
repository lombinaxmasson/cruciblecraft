- 不创建 T27 builder/readiness；

### 0.2 T27 的一句话判据

> open item，令每个 identity 拥有唯一 CC 映射、disposition、owner、依赖、

## 3. 每条记录的统一 schema

每个 canonical identity 至少有：

```json
{
  "table": "recipe_maps",
  "canonical_id": "gt.recipe.example",
  "source": {
    "revision": "3703e40308c8c030763fd6297dea8b210d2a77b1",
    "artifact": "tools/t13_denominators/recipe_maps.json",
    "artifact_sha256": "<current>",
    "record_sha256": "<canonical record>"
  },
  "t13_classification": "in_scope",
  "cc_implementation": "cruciblecraft:example",
  "disposition": "v1_required",
  "reason": "<reviewed reason>",
  "owner": "<exactly one owner>",
  "dependencies": [],
  "replacement_condition": "<machine-verifiable condition>",
  "recheck_point": "<named milestone>",
  "axes": {
    "closure": "<closed/incomplete/not_applicable + evidence>",
    "fidelity": "<source_backed/source_derived/design_policy + evidence>",
    "load": "<measured/projected/pending/not_applicable + evidence>"
  }
}
```

### 3.1 字段规则

`canonical_id`

- 在其表内唯一；
- 不使用展示名作为主键；
- 一旦进入 portfolio，重命名必须保留 lineage。

`source`

- 必须钉固定 revision、输入 artifact hash 与记录 hash；
- 只写文件路径不算来源绑定；
- 当前 source hash 变化时，T27 artifact 必须 stale。

`cc_implementation`

- 写一个规范化 implementation descriptor 或显式 `"none"`；
- 多对一/一对多映射要在 descriptor 中列别名和证据，不能伪造成一对一；
- 注册但零 logical 的槽位不能写成“已实现 source map”。

`disposition`

- 只能是 `v1_required`、`post_1_0`、`out_of_scope`；
- 不允许空值、`deferred`、`todo` 或自造同义词；
- `v1_required` 表示产品契约已经要求，不是“看起来重要”；
- `post_1_0` 必须有 owner/replacement/recheck；
- `out_of_scope` 必须有明确排除理由。

`owner`

- 每个 `v1_required` 和 `post_1_0` 恰好一个 owner；
- 可以先用稳定 owner key，例如 `portfolio:v1/crucible`；
- T28+ 拓扑生成后，v1 owner key 必须解析到唯一 generated card；
- 不能同时归给两条内容轨。

`dependencies`

- 引用 canonical id、open-item id 或明确的 runtime capability；
- 目标必须存在；
- 图必须无环，或对允许的测量环给出独立解环卡；
- 不能写自由文本“依赖以后实现”。

`replacement_condition` 与 `recheck_point`

- 条件要能判断真假；
- 时间点使用命名里程碑，不写“有空”“以后”；
- `post_1_0` 不能用永久 deferred 掩盖无 owner。

三轴：

- closure：集合完整性、玩家可达性、未完成边界；
- fidelity：来源、转换和设计策略；
- load：独立 hard axis 的 measured/projected/pending；
- 未测量必须是 `BLOCKED_PENDING_MEASUREMENT`，不得填 0。

### 3.2 统一即时门禁

每个七表子卡合入前必须满足：

```text
input canonical set == output canonical set
duplicates == 0
missing == 0
unexpected == 0
unclassified == 0
owner violations == 0
broken dependency refs == 0
```

集合全等比较使用 ID 集合和 record hash，不用数量相等代替。

### 9.2 载荷权威轴

`tools/t14_load_budget_policy.json` 是唯一机器可读门禁。特别是：

```text
eager_publication_rows:
  soft = 18,000
  hard = 21,000

lazy_logical_rows:
  soft = 16,000
  hard = 56,000

datapack_authored_entries:
  soft = 6,000
```

所以“21,000”属于 eager hard ceiling。旧 T22/T22.5 文档中的
`logical = 21,000` 不再作为独立权威门禁。

其他轴也必须保留：

- lazy cache 1,024 / 4,096；
- sync 16 MiB / 64 MiB；
- server reload 5 s / 10 s；
- server index 500 ms / 1 s；
- client reload 5 s / 10 s；
- client index 1 s / 3 s；
- retained memory 128 MiB / 512 MiB；
- allocation 128 MiB / 512 MiB；
- lookup p95 1 ms / 2 ms；
- lookup candidates 64 / 128。

两个轴的余量不能相加成“统一容量池”。source rows、authored rules、datapack files、
logical/eager/lazy 也不能互相换算。

## 11. T27-6 · 确定性生成 T28+

### 11.1 输入集合

只选择：

```text

AND closure != closed
```

`post_1_0`、`out_of_scope`、F003/F005 RC recheck 不进入 v1 implementation 拓扑。

### 11.2 算法

1. 对剩余 v1 set 构建 dependency DAG；
2. 若有缺目标或环，T27 失败；
3. 按拓扑层排序；
4. 同层使用稳定 tie-break：
   `table + canonical_id + owner_key`；
5. 只有拥有同一可独立闭合玩家路径、相同 fidelity/load 边界的项才允许合卡；
6. 每张 generated card 单独列 closure/fidelity/load 入口和退出条件；
7. 从 T28 开始连续编号；
8. 由 builder 生成 card list 和 owner resolution；
9. 输入不变时输出字节完全相同。

不得在算法前写“必然是 T28/T29 两张”。即使当前人工判断只有 crucible 和 O-36，
最终张数也必须由实际未关闭集和依赖图计算。

### 11.3 RC 规则

- 剩余 v1 set 非空：只生成 T28+ implementation cards，不生成 RC 编号；
- 所有 generated v1 cards 后续实际关闭：下一次 portfolio replay 才允许派生 RC；
- RC candidate 必须接回 F003/F005 重测；
- 不在 T27 抢占未来 RC 的具体 T 编号。
