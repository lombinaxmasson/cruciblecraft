本文件是 T44 Storage bundle 的签发计划。它不能代替 R0 work set、source
receipt、load measurement、census delta、topology 或 readiness。关闭后的权威 overlay
是 `tools/t44_card_topology.json` 与 `tools/t44_readiness.json`；T43 / T36-Repair JSON
保持只读，不重写历史 `T44 unassigned` 正文。

T44 是内容 bundle，不是 ordinary recipe wave：624 个 registration 不计入 ordinary
recipe family universe，也不以注册数、资源文件数或 creative-tab 可见性减少 recipe gap。
它仍受“同一时刻只有一张 active 内容卡”的串行约束，并必须像 recipe wave 一样具备
source、runtime、玩家路径、load 与 census 的可审计闭环。

## 2. 来源、冻结与可复现性

### 2.1 Source oracle 约定

`gt6_referencable_port_code/gregtech6_w` 是当前所称的 `gt6_w`：NeoForge port 的参考
实现树。T44 使用它来追踪 Storage MTE 的字段、库存规则、方块状态、交互与表现层；
CrucibleCraft runtime 仍使用自己的 Block、BlockEntity、menu/capability 与配方系统。

`tools/t35_storage_scope.json` 中的
`source_revision = 3703e40308c8c030763fd6297dea8b210d2a77b1` 是既有 Storage 分母的
历史 pin。R0 不得把它静默替换为 `gregtech6_w` 的工作树状态。T44 receipt 必须同时记录：

```text
denominator_source_revision     = T35 既有 pin
source_oracle_path              = gt6_referencable_port_code/gregtech6_w
source_oracle_revision          = R0 实测的 gregtech6_w commit
source_oracle_dirty             = false
source_file_hashes              = 实际读取的 MTE/source 文件 hash
normalization_schema_version
selection_sha256
```

若 reference tree 不可用或 dirty，full replay 必须 fail closed；日常 `--check` 则只验证
已提交的 normalized source、receipt 与 aggregate hash，不依赖本地 reference tree。

## 3. R1：数据目录、稳定 ID 与注册投影

建立单一、受 schema 校验的 catalog，而非第二份 Java variant 列表：

```text

src/main/java/.../content/storage/StorageVariantCatalog.java
src/main/java/.../registry/...（catalog-driven Block / BlockItem 投影）
```

每个 catalog entry 至少固定：

```text
runtime_id, source_site_id, source_legacy_id, family, expansion_key
behavior_profile, capacity_profile, inventory_profile, blockstate_profile
model_profile, loot_profile, visibility, acquisition_profile
source revision and source-location lineage
```

stable runtime ID 必须在 lock 中显式映射并做 append-only 验证；不得从当前本地化名称临时
生成。运行时注册数必须与 catalog 一对一校验：

```text

logistics registrations = 1
duplicate runtime IDs   = 0
unmapped source sites   = 0
```

Java 可以有少量按 `behavior_profile` 分派的共享 Block/BlockEntity 实现，但不得为 625 个
registration 写 625 个常量、switch 分支、独立 BlockEntity 类型或手写资源清单。

## 4. R2：行为、资源与玩家取得路径

### 4.1 共享行为的最小等价边界

T44 先建立 profile-level contract，再投影所有 catalog variant。至少分别覆盖：

- **bookshelf**：书位、有效物品过滤、附魔 power/交互、状态与 NBT 保留；
- **bottle crate**：九槽容器、瓶类过滤与插拔规则；
- **drawer**：四分区呈现、库存访问与方块方向；
- **locker / charging locker**：护甲槽、换装行为；charging profile 必须明确 CC 的能源
  映射，且不丢失 locker storage lineage；
- **mass storage barrel / box / standard**：单物品类型约束、容量、自动输入输出、overflow、
  过滤保持/重置与内容持久化；
- **storage inserter**：投放与邻接扫描语义，以及每 tick 扫描范围、工作量和失败条件；
- **mass storage logistics**：独立 profile 与现有 CrucibleCraft logistics capability 的
  适配证据，不能只是标准 mass storage 的换皮。

没有逐 profile 的 source-to-runtime semantic diff 与正/反例测试，不得宣称“共享行为
已等价”。

### 4.2 表现层、掉落与可取得性

catalog 必须驱动生成或验证每个公开 registration 的：

```text
Block + BlockItem
blockstate, block model, item model, lang, loot, tags
creative visibility, source-backed acquisition/disposition
```

source-hidden、invalid 或不可生存获得的行可以保留稳定 identity，但须标为
`source_hidden` 并有来源理由；不得为凑“全部可取得”伪造 recipe。对 source-visible 行，
玩家路径必须从 T44 外部 B0 基线出发，所有支持性输入均已可取得。创造栏可见或测试注入
不能成为生存取得证明。

破坏、爆炸、wrench/拆卸（如适用）及重载时的 contents/NBT 保留策略必须明确，并同时有
正面与数据丢失反例测试。

## 5. R3：验证与 load gate

### 5.1 生成和 runtime 验证

1. Python：source → catalog → generated assets 可重放；正常 `--check`、full replay、
   receipt/hash/currentness 都通过；
2. Java：catalog 等于 live registry；行为 profile 的 inventory、filter、capacity、
   serialization 与 capability 测试完整；
3. GameTest：放置、交互、自动化、破坏/掉落、reload 后持久化，以及 locker charging、
   mass-storage overflow、logistics/inserter 的代表性正反例；
4. 数据生成：连续两次 datagen 无漂移；server/dedicated-client datapack reload、model bake
   和同步均成功。

代表性 GameTest 不能替代 625 行 registration 覆盖；行级 coverage 由 catalog-driven
harness、registry/asset/loot/acquisition validation 共同提供。

### 5.2 Load 与性能

T44 必须在 card-only 和 integrated current 两种场景实测：

```text
server/client startup and reload
registry construction, model bake, sync payload, retained memory and allocation
BlockEntity persistence and ticking
inserter/logistics worst-case scan, transfer and queued work
```

测量记录须包含样本、硬件/运行配置、p50/p95/max、基线、delta 和结论。不得把零测量、
单次开发机截图或未创建 BlockEntity 的测试写作通过。T14 hard ceiling 不能因 T44 上调；
无法满足时保持 `BLOCKED` 或缩小并重签 lock。

## 7. T44 后的排程原则

T44 后不预写 T45 的 host 或 family IDs。下一个 R0 依序处理：

1. **Bath MTE treatment/reconditioning audit**：冻结 source-object、浴液和 MTE 参数的
   公共语义；它是 blocker audit，不可拿所有 Bath 行套一个无条件模板。
2. **跨 host block-object cohort**：在 Bath 审计后，对可共享且全部满足 B0/runtime 的
   Smelter/Drying block object family 建 production lock；当前 owner 量级约为 397，实际
   completion 仅取 R0 冻结的完整 family。
3. **material form / molten cohort**：先补齐 source material、form、fluid 与真实取得路径；
   当前 form/fluid/mixed owner 总量约为 292，不将它们机械相加伪装成已关闭 family。
4. **Mixer bulk**：先正式实现并验证 `ParameterizedSpec`，然后才以 parameterized
   generation 处理其约 664 families / 7,193 rows 的历史规模。
5. **recycling**：当前 gap 内约 829 个 evidence-needed family 与 deferred ledger 的
   1,817 个 `later:recycling` family 分开证据化和关闭；后者不属于 3,076，但仍阻挡
   1.x exit。

后继 recipe wave 一律执行 source freeze → production lock → generation → 全 relation
equivalence → 玩家路径 → 实测 load → census，不以 template、JSON、注册或 reclassification
替代 complete-family closure。
