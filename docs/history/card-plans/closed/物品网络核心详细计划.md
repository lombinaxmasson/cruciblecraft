## 0. 决策

工具头前缀折回已关。账本下一张是 Item Network Core。R0 冻了七个
logistics cover kind，可行性 `requires_new_runtime`，游戏里仍然没有
封面网。R0 `allows_core_child = false` 只禁止从 R0 topology **预分配**
后继，不禁止账本另签一张实现卡。

本卡是那张实现卡，但只收物品切片。签发当下把三套容易混的名字拆开：

| 名字 | 账本位置 | 是什么 | 本卡 |
| --- | --- | --- | --- |
| Item Network Core | 账本后续顺序里的人类名 | 物品介质封面网运行时 | **本卡** |
| `logistics_item_storage` / `logistics_item_transfer` | R0 七 kind 里的物品两行 | `CoverLogisticsItemStorage`；`CoverLogisticsItemExport` + `CoverLogisticsItemImport` 已按 direction 折成一行 | **只收这两行** |
| `logistics_core` / `MultiTileEntityLogisticsCore` | R0 `inherited_denominator.logistics_core`；排除表 family `logistics/multi_tile_entity_logistics_core` | GT6 多方块控制器（能源 / 结构 / 流体口 / 服务器 tick） | **不包含** |

「Core」指 **物品网运行时核心**（身份、发现、物品存取、持久化、服务器证明），
不是 GT6 那台叫 Logistics Core 的多方块。不得把本卡写成
`logistics_core` 已开工，也不得把 R0 `allows_core_child = false` 读成
「永远不许做物品网」。

Fluid / Generic / Dump 仍 `frozen`，留给账本上的 Fluid / Generic
Network。本卡不得顺手把那五行走进 Java。

```text
runtime/item-network-core
```

## 1. 完成后应该成立的工作流

```text
inherit R0 item kinds only
  logistics_item_storage
  logistics_item_transfer   # import/export = direction data
  -> add cover definitions + behaviors
       do not pretend conveyor / retriever / robot_arm are the net
  -> network identity: cover join / leave
  -> discover endpoints only inside a physical connectivity component
  -> storage kind declares queryable item inventory
  -> transfer kind routes by direction data
       unknown kind / unknown direction = fail-closed
  -> persist cover config + identity across reload and chunk unload
  -> measure three axes separately:
       player acquisition
       network / save
       dedicated-server behavior
  -> plus load (scale) on its own axis
  -> ITEM_NETWORK_CORE_READY
       or BLOCKED
```

关键分界：

1. 七 kind 分母仍只读继承。本卡实现其中两行，不改 R0 artifact 正文，
   不把另外五行改成 complete。
2. import / export 是 **同一** `logistics_item_transfer` 行为上的方向数据，
   不是两套 Java behavior。方向合法值实施时钉死；缺省、拼错、未知值
   fail-closed，禁止 silent no-op。
3. 端点发现必须同时满足：同一网络身份 **并且** 落在物理连通分量里。
   只有身份、没有连通，不是一张网。只有相邻管道搬运、没有身份，也
   不是本卡。
4. `mass_storage_logistics_6200` 可以当物品 endpoint，不能变成 cover。
5. 玩家获取、网络/存档、服务器行为必须分轴测量，不得共用一台机器或
   一个能源 owner 的 census。
6. 关卡后账本第 1 节物流行写成「物品两行已由本卡实现」，Fluid /
   Generic / Dump 与 `logistics_core` 继续 `frozen`。不得写成七 kind
   `player_complete`。
7. 关闭后 `next_unassigned = true`。下一张仍是 Fluid / Generic
   Network，本卡不预分配。

## 3. 权威分母与命名

### 3.1 本卡收的两行

只读继承 R0 `inherited_denominator.json` / `source_semantics.json` 里
已经冻结的两行，不得改名、拆分或把方向重新拆成两个 kind：

| canonical_id | 介质 | 角色 | raw members | 方向 |
| --- | --- | --- | --- | --- |
| `logistics_item_storage` | item | storage | `CoverLogisticsItemStorage` | 无 |
| `logistics_item_transfer` | item | transfer | `CoverLogisticsItemExport`, `CoverLogisticsItemImport` | 数据 |

storage 回答 R0 `storage_policy`：如何声明网上可查询的物品库存。
transfer 回答 R0 `routing`：方向变体如何寻址 **非相邻** 但物理连通的
端点。identity 回答封面如何加入 / 离开一个物流身份。

封面物品数实施时自定（两件或三件），但 kind 计数必须仍是 **2**。
不得为了「导入板 / 导出板好看」再登记一个新 canonical_id。

### 3.2 签发决定：不包含 `MultiTileEntityLogisticsCore`

| 事实 | 值 |
| --- | --- |
| R0 域 | `multiblock_kinds`，不是 cover kind |
| 源符号 | `MultiTileEntityLogisticsCore` |
| 排除表 family | `logistics/multi_tile_entity_logistics_core` |
| 源登记 | `loader:Logistics\|17997\|…` |
| R0 纪律 | `logistics_core` 仍是多方块；`allows_core_child = false` |

不包含的理由：

1. 用户签发范围只点了物品两行 + 身份 / 发现 / 方向 / 持久化 / 服务器证明。
2. 该多方块自带能源、结构、流体口和服务器 tick，会撑破物品切片。
3. 账本里「Item Network Core」与 `logistics_core` 只是英文撞名。
   本签发把它们写成两行，不再共用一个「core」后继。

后卡若要做这台多方块，必须另签，并单独回答结构 / 端口 / 事务 /
UI / 获取。本卡 topology 不预写那个后继。

## 4. 运行时契约

R0 `network_contract.json` 的七个问题，本卡只答物品切片能答的：

| 问题 | 本卡答案 |
| --- | --- |
| `identity` | 封面显式加入 / 离开一个物流身份。卸下、改身份、销毁宿主都要 leave |
| `routing` | 只对 `logistics_item_transfer`。方向是数据。寻址物理连通分量内的端点，不是全世界同号广播 |
| `storage_policy` | 只对 `logistics_item_storage`。声明网上可查询的物品库存；可把已有 `ILogisticsStorage` endpoint 标成可查询，但不能把那台柜子改成 cover |
| `dump_policy` | **不答**。Dump 不在本卡 |
| `save_sync` | 封面配置 + 网络身份进存档；reload 与 chunk unload 后仍在；unload 期间不可见，reload 后重新 join |
| `load` | 玩家获取、网络/存档、dedicated 行为、规模负载分轴测量 |
| `fail_closed` | 未知 kind、未知方向、身份对不上、连通断开：禁止 silent no-op |

### 4.1 身份

- 每个参与封面属于至多一个物流身份。
- join / leave 必须可观察：卸下封面、改身份、打掉宿主、卸载 chunk
  都要更新网上可见集。
- 空身份或未知身份 fail-closed：不当成「默认全服一张网」。

### 4.2 物理连通发现

DESIGN_POLICY（本卡钉死，实施时写出谓词，不得事后改成无线）：

```text
可见端点 = 同一维度
        ∩ 已加载 chunk
        ∩ 同一网络身份
        ∩ 同一物理连通分量
```

物理连通分量必须是可走的图：物品管、方块邻接，或二者的冻结组合。
实施时把谓词写成 SOURCE_DERIVED / DESIGN_POLICY 并配回归。禁止：

- 同身份、无视距离的世界广播；
- 把相邻 conveyor / retriever / robot_arm 的 `activeTransfer` 冒充本卡
  发现；
- 把未加载 chunk 里的端点当成还在。

无目标：网上没有合法 sink / source 时，transfer 必须停并且可测，
不是悄悄吞物品。目标移除：端点消失或 leave 后，下一次发现不得再
走到它。

### 4.3 持久化

必须活过：

- 世界 save / 进程重启；
- `/reload` 或等价资源重载（封面定义仍能解析到同一 behavior）；
- chunk unload → 再加载。

unload 期间该端点从发现集消失；配置与身份不得丢。再加载后自动
join 回同一身份。禁止「只 RAM 里有网，重进世界就散」。

### 4.4 获取与测量轴

R0 overlay 的 `replacement_condition` 对本卡两行仍然有效：

```text
player acquisition
network / save
server behavior
```

三轴不能共用一台机器 census，也不能挂到能源 owner 上充数。
规模负载是第四轴：端点数 / 发现访问量 / 单 tick 搬运必须有上界，
并单独记账。不得把相邻管道的旧 traversal 计数拿来当本卡 load
winner。

玩家必须能在生存里做出（或等价获得）物品 storage / transfer 封面。
只进创造栏不算 acquisition 轴关闭。

### 4.5 现有栈怎么用

| 机制 | 本卡用法 |
| --- | --- |
| 9/8 相邻封面栈 | 只读基线。可以新增 definition / behavior，**不许**把 conveyor 改写成物流网 |
| `ItemPipeNetworkTraversal` | 可复用或对照其「已加载、有上界」的走图纪律；它不是本卡身份网 |
| `ILogisticsStorage` / `mass_storage_logistics_6200` | 可选 endpoint，不是 cover |
| `CoverBehaviorRegistry` 未解析 → fail-closed | 保持；未知 logistics kind 必须落到这条，不得 no-op |

`CoverResourceTest` 若写死 9 行 definition，实施时按新权威改断言，
禁止为了绿测把新封面藏起来。

## 7. 撤回

实施中发现阻塞时只有三种合法结果：

1. 在本卡内收紧连通谓词或封面件数，但 kind 仍是那两行；
2. 保持 `BLOCKED`，写清缺的是身份、发现、存档、获取还是 dedicated；
3. 正式撤回并重签，保留本计划日期与排除决定。

不得用相邻 conveyor 冒充物品网。不得把 Fluid / Dump / 多方块塞进来
凑「看起来像 GT6」。不得改写 R0 `feasibility.json` 来假装本卡是 R0
child。不得把七 kind 标成 `player_complete`。

关闭时：本计划移到 `card-plans/closed/`，补 stage archive 与 work
log；更新 history index、roadmap、workflow、verification 与账本
第 0 / 1 节；不重写 sealed R0 artifact；不自动创建 Git commit。
