# 验证精简与动态测试契约详细计划

> 计划 slug：`tooling/verification-slimming`
> 状态：已关闭（2026-09-08）。本文件位于 `card-plans/closed/`。
> 先行测试契约已落地；card-fast / 晋级分层 / Gradle 隔离尚未实施，
> 不占 unique active，后续另开卡认领。
> 性质：把“内容卡改动必须手工刷新全局计数、重复抄 GameTest 名单、重跑
> 全部已关闭能力”这条验证路径收缩为按影响面执行的动态契约。
> 本卡是验证工程卡，不拥有游戏内容、配方 family、机器、流体或玩家路径。

本卡回应本 revision 的实际验证记录：热流体实现本身已经有独立的
16 条 GameTest 和 11/9/8 source matrix，但一次完整 `gradlew test` 要运行
879 个 JUnit；生成语言文件增加键后，测试仍因为全局 `en_us` / `zh_cn`
总数失败；registry identity 测试也把全仓库条目数写成固定整数；电池
`required_test_ids` 在 Java 已经增加测试后，Python 又维护了一份需要手工同步
的名单。验证失败还曾被 Gradle test worker 持有的
`build/test-results/test/binary/output.bin` 放大。

权威边界：

- [能力交付流程](../../../current/capability-delivery-workflow.md)；
- [开发与验证指南](../../../current/verification.md)；
- [冻结与未实现账本](../../../current/unimplemented-gap.md)。

本卡不把旧 receipt、历史 seal、`*_READY` 或“上一次跑过”当作当前证据。

## 1. 现状分类

### 1.1 必须保留的来源合同锁

这些数字描述的是某张卡明确拥有的来源分母，不能改成“只要非空”：

- `energy/nuclear-fission-hot-fluids` 的 11 source branches、9 owned
  conversions、8 hot identities；
- 电池卡的 37 个 GT6 battery loader rows；
- 配方 family、生产 lock、source matrix 和 census 中已经签发的分母；
- 机器的行为集合、槽位几何和协议字段。

新增内容如果改变这些分母，必须修改它所属的 source-backed catalog、capability
声明和卡测试；不能只让测试自动适应。

### 1.2 应由当前来源推导的投影计数

以下数字不再作为手工维护的硬编码：

- `ProcessingMachineResourceTest` 的整个 `en_us` / `zh_cn` 键总数、已翻译数、
  缺失数和复制英文数；
- `RegistryIdentityTest` 的全局 `live_entry_count`；
- generic cell 的总行数、FLUID / GAS 分拆数以及 container gate 总行数；
- `CrucibleCraftGameTests` 中把 chemical / cell / material prefix / handshake
  总数写死的断言；
- `HydrocarbonFluidGateTest` 的当前全局 chemical entry 总数。

这些测试改为验证关系、不变量、来源对象存在性、唯一性和非空性。新增一个
合法 fluid、material 或 translation key 不应要求编辑测试里的旧总数。

### 1.3 应以 Java 为真相的测试 ID

`capability.json` 中的 `required_test_ids` 仍是审查用的显式声明，但
`tools/tests/test_player_complete.py` 不再为每个 capability 再抄一份 Python
列表。方法发现器读取 capability 的 owned Java paths，测试只校验：

```text
declared required_test_ids == owned Java @GameTest method ids
```

这样新增或改名测试时，只需更新能力声明；不会再同时更新一份没有运行时
权威性的 Python 常量。

## 3. In scope

### 3.1 动态测试契约

- 把全局 census 数字断言审计为四类：来源分母、派生投影、运行时行为、性能
  / 载荷预算；
- 只有来源分母和明确的协议预算保留 exact count；
- 派生投影统一从 gate、catalog、manifest 或运行时 registry 的当前对象
 计算期望值；
- 为动态关系增加重复、缺失、越界和 namespace 检查，避免“改成非空”后
  失去实际保护；
- 为 test helper 提供统一的 `assertDeclaredGameTests` / projection-count
  helper，避免同一政策散落在多个类。

### 3.2 影响面驱动的日常验证

设计并实现一个本地 card-fast 入口，按 changed paths 和 capability owned
paths 选择：

- Python 合同测试；
- `compileJava` / `processResources` / `runData` 中真正受影响的任务；
- 受影响 package 或 capability 的 JUnit 子集；
- 对应 namespace 的 isolated GameTestServer。

普通内容卡不重跑已接受且没有被 impact graph 命中的其它 capability。

### 3.3 晋级与 release 分层

- `runtime_ready → player_complete`：只运行本次发生 maturity promotion 的
  capability；执行其 fresh GameTestServer，必要时执行 `runClient`；
- 已接受 capability 的普通改动：只跑受影响的 capability-runtime / card-fast
  门，不自动跑所有 `player-complete` builders；
- release：保留全 profiles、全量 JUnit、全量 datagen 和所需 client smoke；
- 任何 profile 被 SKIP 时，在报告中写出“无 owned path 命中”的原因，不能
  用旧 receipt 代替 PASS。

### 3.4 Gradle 执行可靠性

- 同一 checkout 同时只允许一个 Gradle test / datagen job 写共享
  `build/test-results`；
- 不在任务运行期间调用 `gradlew --stop`；
- 若需要并行 profile，使用隔离的 test result / run directory；
- 失败时区分真实测试失败、进程被停止、文件锁和外部下载 / 认证失败；
- 报告中记录一次命令的开始、结束、exit code 和是否被中止，避免把
  `output.bin` 锁误报成代码回归。

## 5. 实施阶段

### A. 测试来源审计

1. 扫描 `src/test/**`、`src/main/**/GameTests.java` 和 `tools/tests/**` 中的
   `assertEquals(N, *.size())`、`== N`、重复测试 ID 列表。
2. 给每一处标注 `SOURCE_CONTRACT`、`DERIVED_PROJECTION`、
   `RUNTIME_BEHAVIOR` 或 `PERFORMANCE_BUDGET`。
3. 对 `DERIVED_PROJECTION` 替换为关系断言；对误删的保护补充 duplicate /
   missing / source-to-runtime 对应测试。
4. 加一个 Python 静态检查，禁止新代码在 active verification owned paths
   中写没有来源注释的全局 catalog count。

### B. card-fast profile

1. 在 `verification_profiles.json` 增加 card-fast 的 profile 合同和 builder
   选择规则。
2. 在 `verify.py` 中输出 changed paths → selected profile → selected test /
   Gradle task 的解释性计划。
3. 为 Java 源、Java 测试、datagen provider、generated resources、能力文件和
   docs 分别定义最小任务集。
4. 为 capability runtime wave 只运行其 owned GameTest namespace；不把所有
   `@GameTestHolder` 合并到同一次本地卡验证。
5. 保留 `--if-changed` 的无 diff base 安全行为，但让本地明确 capability
   参数可以绕过 Git diff 直接选择一张卡。

### C. promotion / release 分离

1. 复用 `capability_ledger.player_complete_promotions(base)` 选择晋级卡；
2. 禁止普通 `dev` 因为共享 `tools/player_complete.py` 而启动十张已接受卡；
3. promotion 运行新晋级卡的 server + client；
4. release 运行全量 profile，并生成一份可读的耗时分解；
5. 加测试锁定：accepted capability 不会因未命中的 owned path 被重复
   GameTest。

### D. Gradle 隔离和耗时证据

1. 先测量当前 cold / warm `compileJava`、focused test、full test、runData、
   单卡 GameTestServer 和全 player-complete 的 wall time。
2. 为共享输出目录增加并发保护或隔离策略。
3. 失败报告区分 test failure、worker lock、daemon stop、download timeout。
4. 不以“本地更快”为唯一验收；比较执行的测试集合和结果完整性。

## 7. 预期结果

内容开发的默认路径从：

```text
改代码
  -> 全量 JUnit
  -> 全量 capability-runtime
  -> 全部 player-complete
  -> 再跑本卡
```

收缩为：

```text
改代码
  -> changed-path card-fast
  -> 本卡 focused JUnit / GameTest
  -> 只有发生 promotion 才跑本卡 client
  -> release 时再做全量闭合
```

目标不是让门变松，而是让失败对应真正的变更边界，并让新增内容不再因为
无来源的历史整数或重复名单要求手工维护。
