### 0.5 八条硬规则

1. **先取证，后注册。** 60 条清单能从固定源完整提取；不实现一个 baseline 再补 59 个。
2. **flat list 是契约。** API 只给 `entries()` / `variantsOf(kind)` /
   `require(id)`，不得提供 `tierOf(kind,n)`。
3. **新子系统全前缀。** 只允许 `<material>_<kind>`；不注册裸 `hopper` /
   `queue_hopper`。
4. **旧 ID 冻结。** `machine_tiers.json` 当前 33 条旧机器变体不重命名；裸 tier-1
   是 legacy baseline。
5. **一个 Hopper Block 类 + 一个 variant record。** 材料不产生 Java 子类；
   normal/queue 差异由 kind strategy 驱动。
6. **注册与资源同时闭合。** 不允许 block 已注册但 item/model/lang/loot/recipe 缺失。
7. **自动 JSON 只由 builder/Datagen 写。** 不手改派生计数、hash、readiness。
8. **验证失败不向下游扩散。** 同一检查无新证据连续失败两次就停，先定位根因。

### 1.1 三种数量不要混写

```text
60 source base rows
→ 120 derived block variants
→ 121 total new blocks including Dust Funnel
→ 121 acquisition recipes（若每个 identity 一条）
```

它们不是同一个计数。Datapack 轴还会包含 loot/catalog；客户端资源还包含 blockstate、
item model、共享 parent/texture。最终以 builder 和 Datagen 实测为准。

### 1.2 配方保真边界

GT6 Hopper 配方使用 `plate` + `plateCurved` + chest，并包含不消耗的工具字符。
CC 当前：

- 60/60 材料都有普通 `plate`；
- 没有运行时 `plateCurved`；
- 原版 shaped crafting 不能直接表达 CC 材料工具“使用但不消耗”。

因此 T30 固定：

- Hopper：5 plate + 1 chest；
- Queue Hopper：5 plate + 2 chest；
- 省略工具催化剂；
- acquisition 标为 `SOURCE_DERIVED`；
- 不借配方实现偷偷增加 `plateCurved`。

Dust Funnel 源配方继续使用 vanilla hopper + iron plate/rod 的等价结构。

### 3.1 什么是真正线性的

以下不能交换顺序：

- R0 在所有写入之前；
- R1 的 60-row 清单和命名冻结在任何新 registry id 之前；
- R2 的旧 ID 快照测试在旧机器注册重构之后、Hopper 注册之前；
- R4 注册与 R5 行为不能跨长期红树；最迟同一集成波次闭合；
- R5/R6 行为绿后才生成最终 Datagen 集；
- JUnit 全绿后才跑 GameTest；
- builders/pin-chain 在运行时和资源集合稳定后；
- snapshot 冻结后到 record 完成零编辑。

### 3.2 哪些可以并行

只有满足“不改同一文件、不启动两个写 builder、不争用 Gradle/run 目录”时：

- R1 source parser 与 Phase 5.1 合同文案可以并行开发，汇合时由同一 builder 校验；
- R3a、R3b 是两个纯 Java 核，可由不同人并行；
- R3c 可并行审查/制作共享美术资产，但不能提前写 120 个 blockstate；
- R3d 可先做 1/2/36 槽布局算法和纯测试，不接注册；
- Hopper GameTest 设计与 Dust GameTest 设计可以并行写草稿，最终写入
  `CrucibleCraftGameTests.java` 时串行合并；
- 英文/中文命名规则可并行审查，最终由同一 Datagen pass 写出。

### 3.3 看起来能并行、实际不能并行的部分

- `ModBlocks.java`、`ModItems.java`、`ModBlockEntities.java` 的两套功能写入；
- `ModBlockStateProvider.java` / `ModLanguageProvider.java` / loot/recipe 的两套循环；
- 两个 `runData`；
- JUnit 与 GameTest；
- 两个 Python `--write` builder；
- full verification 与任何编辑；
- T31 的封板工作。

这些共享文件或目录太多，并行只会制造不可审查的冲突。

## 7. R3 · 可并行的纯核、GUI 布局与美术准备

### 7.1 R3a · Hopper/Queue 纯搬运核

建议先写无 BlockEntity 依赖的 helper/core，负责：

- simulation-first item insert/extract；
- 普通 Hopper `mode = 0..64`；
- `mode=0, exact=false`：本轮最多 64；
- `mode=0, exact=true`：一次最多一 stack；
- `mode=n, exact=false`：只搬可整除的 n 批，单轮总量不超过 64；
- `mode=n, exact=true`：只在完整 n 可交付时搬一次 n；
- Queue 首槽输入、末槽输出、内部向后推进；
- Queue `slotSize = 1..64`；
- 任何目标拒绝/部分接受时守恒；
- 不复制、不吞物、不越过 ItemStack max。

立即验证纯 JUnit。至少覆盖 0/1/64、目标只剩部分空间、不同物品、NBT components 不同、
simulate 与 execute 不一致时 fail closed。

### 7.2 R3b · Dust 36-unit 纯账本

固定单位：

```text
dust       = 36
small_dust = 9
tiny_dust  = 4
```

规则：

- 内部一次只允许一种 material；
- 输入可混合三种 size，但 material 必须相同；
- 输出模式 dust/small/tiny；
- 只在完整 36-unit batch 时分别输出 1/4/9；
- batch 以下余量继续保存；
- break 时能用原三种 form 精确分解，若设计不能保证则把余量放进掉落 BlockItem
  的持久组件，禁止静默丢失；
- 序列化使用整数，不用 float。

立即验证：

- 9 tiny → 1 dust；
- 4 small → 1 dust；
- 1 dust → 4 small / 9 tiny；
- mixed size 守恒；
- mixed material 拒绝；
- 多次 save/load 后单位不漂移；
- 输出堵塞不扣内部量。

## 9. R5 · Hopper / Queue Hopper 运行时接线

### 9.1 方块状态与朝向

- placement 保存输出 facing；
- 默认向下；
- 至少支持下与水平方向；
- 若保留向上 facing，必须明确 GT6 的“不主动输出”语义并有测试；
- redstone 输入暂停主动 pull/push，但 capability 被动访问仍按规则工作；
- 方块 shape 与模型朝向一致。

### 9.2 BlockEntity 状态

至少持久化：

```text
schema version
variant id / kind identity（或从 block state 安全恢复）
inventory
normal mode
normal exactMode
queue slotSize
cooldown/check state（若需要）
```

未知/未来 schema fail closed，不丢 inventory。variant 与 block 不匹配时隔离或恢复为
block variant，不能悄悄改槽数并吞掉尾部槽位。

### 9.3 主动搬运

每个 server tick/调度周期：

1. 若 redstone 禁用，停止主动动作；
2. 从上方 capability 拉入；
3. 上方无 inventory 且空间允许时吸取 item entity；
4. 普通 Hopper 内部合并相同 stack；
5. Queue 将 slot `i-1` 向 `i` 推进直到稳定或到操作上限；
6. 从 facing 向目标 capability 模拟；
7. 只有目标能接受时执行源扣除与目标插入；
8. 每 tick 有固定操作上限，不能因 36 slots 无限 while；
9. mutation 后 `setChanged`，需要时同步客户端。

### 9.4 sided capability

普通 Hopper：

- 非输出面允许插入；
- 输出面按 GT6 边界限制外部提取/插入；
- 内部主动输出不被自己的 sided wrapper 阻断。

Queue：

- 外部输入只见首槽；
- 外部输出只见末槽；
- GUI 可见全部；
- item pipe 接 facing 时能取到末槽输出。

`ModCapabilities.java` 注册一次 Hopper-family item handler，不按材质复制 120 条逻辑。

### 9.5 工具交互

使用已有 material tool item class，不新增一次性工具：

- screwdriver：
  - Hopper 0→64 循环；
  - Queue 1→64 循环；
  - 潜行反向；
- wrench：
  - normal Hopper 切换 exactMode；
  - Queue 不伪造 exactMode；
- 交互结果 server authoritative；
- 客户端消息/tooltip 显示 slots、mode、exact/FIFO；
- 工具耐久按现有 MaterialTool 规则处理。

若 wrench 同时承担旋转，必须固定手势优先级（例如潜行配置、非潜行朝向，或反之）并测试；
不能让同一次点击既旋转又切 exact。

### 9.6 menu / screen

新增一个 menu type 和一个 screen：

- server opening packet 带 BlockPos；
- menu 从 BE 读取真实槽数；
- arbitrary 1–36 slots；
- quick-move 不越界、不复制；
- block 被替换/距离过远后 `stillValid=false`；
- Queue 槽顺序可理解；
- menu 不同步 120 份 material metadata。

## 15. 验证矩阵：立即跑还是合并跑

| 修改类型 | 必须立即验证 | 可在同一整合点验证 | 最终验证 |
|---|---|---|---|
| 60-row 提取器/映射 | builder `--check` + affected | R9 source replay | record |
| Phase 5.1 合同/topology | schema/DAG tests | T30 readiness | record |
| 旧 33 machine 注册重构 | ID 快照 + tier tests | 全量 JUnit | record |
| Hopper catalog/120 注册 | catalog/registration JUnit | R7 resource closure | record |
| transfer core | 纯 JUnit，必须立刻 | BE + GameTest | record |
| Dust 36-unit core | 纯 JUnit，必须立刻 | BE + GameTest | record |
| NBT/schema/menu quick-move | 精确 JUnit，必须立刻 | 全量 JUnit | record |
| blockstate/model/lang/loot/recipe | 第一次完整 `runData` 后资源测试 | 一次资源闭包 | 双 Datagen |
| tint/ART_DERIVED | provenance/resource test | 客户端目视 | record |
| redstone/朝向/item entity/pipe | 可等 R8 一起跑 | 全量 GameTest | record |
| builder policy/pin-chain | 每个 stale builder + affected | Python closure | record |
| snapshot-bound 文档 | `git diff --check` + 对应 currentness | R10 冻结 | record |

原则：

- **数据源、ID、守恒、序列化**改后立刻验证；
- **同一 catalog 的资源投影**等 registry 稳定后整批验证；
- **昂贵世界行为**先用纯 JUnit 缩小风险，再一次 GameTest 合流；
- **最终 record**不替代任何即时测试。

## 16. Windows、禁止命令与安全提交

```powershell
$env:PYTHONUTF8=1
```

```powershell

```
